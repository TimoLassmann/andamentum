# andamentum.epistemic — notes for Claude

Moved from the root `CLAUDE.md`, word for word. Claude Code loads this file when it reads files in this directory.

## Overview

- `andamentum.epistemic` — formal epistemology: evidence/claims/uncertainty entities, deterministic stage gates, pattern-driven work scheduling, multi-agent verification

## Layering

- **`epistemic` MAY depend on `llm_judge`** — one-way; `llm_judge` must never import `epistemic`, enforced by its own conformance test. The dependency is confined to the operation/graph layer, across **three** driver modules — each a bounded FAST-path second opinion (one `Criterion`, bare-`str` model, temperature 0, strictly sequential), never a replacement for the cheap primary judgment, and never able to change a verdict on its own: `epistemic/quality_doubt.py` (**two** TMS destroy gates, one module: `confirm_low_quality` gates invalidation of near-zero-quality evidence, called from `operations/evidence.py`, and `confirm_corruption` gates the `evidence_corrupted` sentinel, called from `operations/scrutiny.py` — a declined destroy at that second gate records a non-blocking caveat uncertainty and leaves the source's weight untouched), `epistemic/direction_opinion.py` (SITE A — confirms the direction of load-bearing evidence whose judgment was one-hot, so entropy carries no signal; bounded per pass and per claim) and `epistemic/scrutiny_opinion.py` (SITE B — a second reading when the deterministic scrutiny weight is borderline; both called from `operations/scrutiny.py`). The three share one record type, `entities/judge_opinion.py`. **Why three and not one:** `thresholds.py` records that small models emit one-hot judgments 53–82% of the time, so a doubt signal derived only from the primary judgment's own distribution is near-zero on most of the corpus — a second, independent elicitation is the only thing that makes the doubt escalation gate fire at all. `epistemic.judgment_signal` and `epistemic.thresholds` deliberately stay **import-free** of it: importing `llm_judge.signals` executes the package `__init__` → `panel` → `elicit` → `pydantic-ai`, and `judgment_signal` is imported by `entities/evidence.py`, a pure-stdlib leaf. The two modules hold one definition of doubt (`normalized_entropy` / `max_mass` / `normalize_three`, and the identical doubt cutoff) implemented twice and pinned equal by a drift test — `epistemic/tests/test_doubt_scale_single_source.py`, which also fails if a leaf grows an `llm_judge` import.

## Evidence providers

**Evidence providers** follow a strict specification documented in `src/andamentum/epistemic/providers/CONTRIBUTING.md`. Read it before adding or modifying any provider. Key rules: providers retrieve and structure evidence, never assess quality (`quality_score=None` always), never truncate content, and return `list[GatheredEvidence]` (empty list on error, never raise).

**Web evidence** comes from `andamentum.deep_research.v2` and from nothing else in `deep_research`. `WebSearchGatherer.gather` makes one `research(query, mode="web")` call with a small budget (`GATHER_MAX_ROUNDS` 2, `GATHER_READS_PER_ROUND` 3) and turns each finding with a verified quote into one `GatheredEvidence`: the content is the page text within `CONTEXT_CHARS` either side of the quote, `source_ref` the work's URL (a DOI link when it has no URL), `structured_data` carries `claim`, `quote`, `quote_verified`, `title`, `site`. A finding whose quote could not be verified is not evidence; the count is logged. `quality_score` stays `None` (v2 scores no finding; the downstream scorer decides). No verified finding returns `[]`, which `ExtractEvidenceOperation` records as an invalidated stub, not as a placeholder item. `WebSearchProvider` (dispatch provider) searches and fetches through v2's `WebSource` over an in-memory store and keeps the provider contract. The search address is SearxNG (`_SEARXNG_URL`, started through podman on first use) or, with `--browser-cdp-url` on `ask`, `verify` and `preflight` (threaded as `browser_cdp_url` through `handle_ask`, `run_research_question`, `run_epistemic_graph`, `get_default_gatherer`), a Chrome over its debugging address; no environment variable carries it.

## Architecture principles and core abstractions

**Epistemic architecture principles** (enforced across the module):
- **P1: Operations are pure transforms.** An operation reads entities, does work (LLM calls, computations), and writes the result back. It NEVER manipulates fields on other entities to signal what should happen next.
- **P2: The graph is the sole flow controller.** Only graph nodes (in `graph/nodes.py`) decide what runs next, based on operation results, entity state, and graph state.
- **P3: Entity fields are data, not signals.** Every field on Claim, Evidence, Objective represents something real — a verdict, a score, a stage. No field exists solely to tell the scheduler what to do.
- **P4: Graph state tracks pipeline progress.** `EpistemicGraphState` (in `graph/state.py`) tracks what work has been done and what needs doing — not entity fields.
- **P5: Operations don't reach across entity boundaries.** An operation on an Uncertainty does not modify Claims. Cross-entity effects are the graph's job.
- **P6: Every node has an explicit contract; routing decisions are data, not implicit imperative flow.** Each `Node` subclass (in `graph/base.py`) declares `reads` (state fields read), `writes` (state fields mutated), `operations` (operation classes dispatched via `_run_op`), and `post_invariants` (predicates that must hold after the node runs). Successors live in the `run()` return type annotation — pyright + pydantic-graph enforce them, and `graph/topology.py:topology()` exposes them as a Python value you can inspect, diff, and assert reachability over (see `tests/test_topology.py`). The recurring "silent dead zone" routing-bug class (where a node returns to a successor that doesn't continue work the claim still needs) becomes structurally detectable rather than benchmark-detectable. Cross-cutting data carried on entities (e.g. `Objective.decomposition` → `entities/decomposition.py:Decomposition`) uses typed Pydantic models, not `dict[str, Any]`, so consumers access fields by attribute and divergent-lookup bugs become impossible.
- **P7: Lazy escalation — each layer asks for what it's missing; breadth comes from demand, not eagerness.** Planning, investigation, scrutiny, and synthesis don't pre-commit to a wide search. Each layer that detects insufficient evidence emits a `Demand` (`andamentum.epistemic.demand.Demand` — a 3-field flat `needs_more` / `justification` / `target_hint` Pydantic model designed for small Ollama models), and the graph routes that demand to the layer that can satisfy it minimally. Evidence gathering (both initial and follow-up rounds) flows through description-driven dispatch (`epistemic_dispatch_provider`): each provider class self-describes via `description`, `query_guidance`, `query_examples`, `output_kind`, and the dispatch agent is invoked once per provider in parallel — it either commits one or two native-syntax queries or abstains. Cross-domain convergence still requires ≥2 independent sources (Reichenbach common-cause), but the system reaches that threshold through per-provider commit/abstain rather than a separate tournament. Investigation rounds add a methodological *angle* on top of the claim: `epistemic_investigate_claim` generates intents (e.g., "adversarial replication"), and the dispatch agent receives the original claim as the subject plus the intent as the angle modifier — queries stay grounded in the claim's lexicon while exploring the intent's dimension. At synthesis, `CheckSynthesisDemand` runs cheap deterministic gates (open-research, no-combined-verdict, stranded-claims, decisive posterior ≥`POSTERIOR_DECISIVE_THRESHOLD` / ≤`1−POSTERIOR_DECISIVE_THRESHOLD`) before the LLM judgment, and on `needs_more=True` loops back to `Scrutinize` for the eligible claims. The load-bearing termination guarantee is the per-sub-claim cap (`PEIRCE_CYCLE_CAP`), not a global give-up budget. Add new "do more work" decisions to this scheme — emit a `Demand` and let the graph route it — rather than reaching for an eager broad-search shortcut.

**Epistemic core abstractions** (understand these before touching `epistemic/`):
- `entities/` — `Objective`, `Evidence`, `Claim`, `Uncertainty`, `Decision`, `Snapshot`, `Artefact` (all `EpistemicEntity` subclasses), plus `decomposition.py` (typed `Decomposition` / `SubInvestigation` for `Objective.decomposition`) and `cap_evaluation.py` (typed `CapEvaluation` for `Claim.cap_evaluation`, the cycle-cap provenance snapshot). `Objective.claim_to_verify` enables seed-claim verification mode (a Pydantic `model_validator` refuses Objectives that set both `claim_to_verify` and `decomposition` — they're mutually exclusive seed modes; `CreateClaims` would silently pick single-seed and discard the decomposition).
- **The verdict object** (`entities/verdict.py`). A run's decision is ONE typed `EpistemicVerdict` — posterior report, per-claim `ClaimVerdict`s with their `EvidenceRef`s, and a `VerdictProvenance` count block. It is built inside the graph by `CombineClaimVerdicts` (via `confidence.build_verdict`, which is its sole constructor), held on `EpistemicGraphState.verdict`, persisted on the frozen `Snapshot.verdict`, and returned as `PipelineResult.verdict`. Everything downstream — the synthesis prose's `> **Verdict:**` line, the CLI, the offline report, the HTML audit report — **renders** it and never re-decides. `entities.verdict.verdict_label` is the only place in the package that compares a posterior against `POSTERIOR_DIRECTIONAL_BREAKPOINT` (a source scan in `tests/test_verdict_single_source.py` pins that), and `display_label` maps the resulting *direction* onto the closed display vocabulary without a second comparison. When adding a consumer that needs "what did this run conclude", read the object — do not derive a label from a number or parse it out of prose. The predecessor fields `Decomposition.combined_verdict`, `CombinedVerdictData`, `Snapshot.combined_verdict` and `WriteAnswerOutput.verdict` were deleted, not deprecated.
- **Snapshot/Artefact indirection.** The final report is reachable from `Objective` via two routes — direct (`Objective.artefact_id → Artefact.content`, the 1-hop signal stamped by `SynthesizeReportOperation`/`SynthesizeInsufficientReportOperation` on completion) and via the immutable freeze (`Objective.snapshot_id → Snapshot.artefact_id → Artefact.content`, the auditable history). Both point at the same `Artefact`. `Objective` does NOT have a `report` attribute; readers looking for "where's the output" should use `Objective.artefact_id` for the load-bearing presence check (e.g. the synthesis stage exit invariant in `graph/stages.py:_check_synthesis`) and traverse the snapshot path when they need the immutable freeze that produced it. Artefacts have `artefact_type` ∈ {`summary`, `insufficient`, ...} — the typed signal that distinguishes a directional verdict from a fallibilism terminal (`SynthesizeInsufficient`); consumers check this field rather than parsing the verdict prose. The run's *decision* travels the same two routes: 1-hop live via `PipelineResult.verdict`, auditable freeze via `Objective.snapshot_id → Snapshot.verdict` (an `EpistemicVerdict`). The offline report reads the frozen one; it never recomputes.
- `gates.py` — `STAGE_GATES` + `validate_promotion`: deterministic, routing-aware checks that must pass before a `Claim` advances stages. Gates query the question type's routing profile and only require tracks that are PRIMARY or SECONDARY — not SKIP.
- `graph/` — pydantic-graph DAG scheduler. 23 nodes with typed return edges and explicit contract metadata (P6). Entry point: `run_epistemic_graph()` in `graph/__init__.py`. Key files: `base.py` (the `Node` class with `reads` / `writes` / `operations` / `post_invariants` ClassVars), `topology.py` (`topology()` reflection helper exposing the graph as a Python dict), `invariants.py` (reusable post-condition predicates like `no_stranded_claims`), `nodes.py` (the 23 concrete node classes).
- `operations/` — pure `BaseOperation` subclasses. Each takes an `OperationInput`, does work, returns `OperationResult`. They do NOT control flow — the graph does.
- `repository.py` — `EpistemicRepository` wraps a `DocumentStore` (from `andamentum.document_store`) — the persistence layer for all epistemic entities.
- `runner.py` — `DefaultAgentRunner` wraps `core.AgentRunner` with epistemic agent registry lookup.
