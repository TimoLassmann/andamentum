# andamentum.whetstone — notes for Claude

Moved from the root `CLAUDE.md`, word for word. Claude Code loads this file when it reads files in this directory.

## Overview

- `andamentum.whetstone` — structured criterion-cascade review over your own drafts. `await review_document(source, *, model)` is the default entry point: pydantic-graph driven, deterministic substrate (sectionize + claims digest) feeding a one-call-per-criterion review with a gap-loop re-grounding pass, optional editor, and synthesis + self-critique. Returns a `ReviewResult` with confidence-tagged `Finding`s, concrete `Edit`s (when `editor=True`), `AuthorQuestion`s, and a synthesised `summary`. Three renderers (`render_markdown`, `render_html`, `render_docx`) consume the same result; the docx renderer feeds an in-tree track-changes machinery (`whetstone.docx`) by handing each `Edit`/`Finding` its own offsets as a span — the reviewer read the annotated document's text, so no matching happens on the write side. A second review round over the first round's output is the same call with a different `author=` — nothing else. Document type routes to one of six pluggable criterion sets (academic / external_communication / essay / tutorial / creative / general) auto-detected via a one-shot classifier or set explicitly. **Reviewer profiles** (`whetstone/pipeline/reviewers.py`) are the named alternative to typing a criteria string: seven of them — `default` (named `default` rather than `general` because `general` is also a document type; it carries the document type's own criteria and probes, so a `default` run is byte-identical to a run before profiles existed), `claims`, `methods`, `framing`, `reader`, `adversary`, `editor`. A profile bundles values the CLI already accepts (criteria, probe ids, editor criteria, tracked-change author) plus a `brief` — a stance, a bar and an exclusion list rendered into the criterion, probe and editor prompts, and empty for `general` so those prompts render exactly as before. `--criteria` / `--probes` / `--editor-criteria` / `--patch-author` override a profile field by field; `resolve()` is the one place that precedence lives and it reports the source of every value, which the CLI prints. **`--reviewer` takes a comma-separated list** and runs them IN SEQUENCE over one unchanged text: no round edits. Each reviewer signs its own comments with the profile's identity, and nothing is written into the file between rounds: the rounds share one unchanged text, so every finding's offsets address the same document and one render writes the result. **The editor runs once, at the end** (`pipeline/editor.py:edit_findings`): by default, or with `editor` anywhere in the list (the same run, refused beside `--no-editor`; `editor` is pulled out of the rounds, since as a round it would run claim extraction, synthesis and self-critique to produce nothing), one editor pass reads every reviewer's findings, tagged by reviewer, plus the reconciliation's disagreements (rendered into its brief as passages NOT to settle), and writes one set of tracked changes signed by the line editor. Per-round editing was the previous design and it produced five reviewers' style passes over one abstract, each rewriting the last one's insertions — tracked changes with no paper underneath; and two findings on one sentence from two rounds could never meet in one call, so the prompt's own conflict handling (one rewrite for two findings, `can_fix=false` for two that pull in opposite directions) could not fire. Pooling is sound only because no round changes the text, so the CLI checks the projection is identical after each round and fails loud otherwise. A single reviewer keeps its in-graph editor, which already sees all of its findings. A list of more than one ends with `pipeline/reconcile.py` — one call that sees every finding by id (`R2.3`), groups the ones that make the same point, and reports where the reviewers disagreed (both positions kept; choosing is the author's judgement). `merge_agreed` then turns each group into ONE finding — the most severe member, `corroborated_by` naming the other reviewers — after checking the ids (unknown ids ignored, a group left with one reviewer merges nothing). One call decides both the summary's agreed list and the merge, so the two cannot disagree; a failed call merges nothing and the summary says duplicates may remain. Also not a flag. All three renderers get the same combined result (`combine_reviews`), each finding tagged by its reviewer via `perspective`; `render_docx(comment_authors=...)` signs each comment by its reviewer. A specialist REPLACES the document-type criteria rather than adding to them — put `default` in the list for both. Checklist mode refuses a list: two probe banks in one run give two coverage tables that cannot be compared, which is the property checklist exists for. Reviewers are orthogonal to document type, so each profile carries a `fits` set and one predicate `fits(*, profile, document_type)` decides compatibility — a miss warns and PROCEEDS (the classifier can be wrong and the user asked for this reviewer), and the warning is written into the report header rather than left in terminal scrollback. Criteria live in `pipeline/criteria.py` as module-level constants that both the type sets and the profiles reference, so each question has one wording; a test asserts identity (`is`, not `==`) so a copy-paste cannot create a second. Novelty is split across that boundary and the split is the point: the **flag** node runs on EVERY review and lists what the draft claims as new (`ReviewResult.novelty_claims`, rendered as a "Claims you are staking as novel" section in all three renderers, omitted when empty); the **search** and **judge** nodes stay behind `--check-novelty` / `check_novelty=True`. Finding the claims costs one call to the model that has already read the whole draft, so it discloses nothing further; verifying them sends those sentences to a search engine, which was never reading the document — not a step to inherit from a default on an unpublished manuscript. The listing is worth having on its own (seven claims came out of a two-page demo draft, several unsupported anywhere in its own text) and it puts `--check-novelty` in front of the reader holding the exact sentences that would be sent. At most `novelty_target_cap=8` claims are flagged and searched. In a reviewer list the whole check belongs to round 1: the CLI passes `flag_novelty=index == 0` (and gates `check_novelty` the same way), so later rounds spend no flag call and the report carries one list. Panel mode (multi-expert simulated peer review) lives in its own graph (`whetstone.pipeline.panel`) and is invoked via the `andamentum-whetstone panel` command. Checklist mode is the third graph (`whetstone.pipeline.checklist`, `await run_checklist(markdown, *, model)` / `await checklist_document(source, *, model)`): instead of the criterion cascade it runs a fixed bank of `Probe`s — one defect class each, phrased as extraction under a quota ("find the 3 claims the evidence supports least well") — and summarises with a deterministic coverage table instead of synthesised prose. It deliberately does NOT reuse `consolidate`, the gap loop, or LLM synthesis: predictability is the product, so the cost is one agent call per probe (tool turns bounded by a per-probe usage limit) on top of the shared claim-extraction pass, the table's rows come from the bank rather than from the findings, and two runs over an unchanged document stay comparable row for row. Style / readability checks live in the separate `andamentum.proofread` module — the two are deliberately disjoint pipelines.

## CLI

|---|---|---|
| `andamentum-whetstone` | Criterion-cascade review of your own draft → markdown / HTML / .docx with track changes. **The default run turns most things on and flags turn them off**: review, editor (`--no-editor`), the reference check with its Crossref lookup (`--no-references`, `--no-lookup`; run BEFORE the review so the editor answers its problems via `extra_findings`, each comment signed by the reference checker, the confidentiality tripwire first inside `references_check.check_open_document`), the novelty list, and a report section "Next step" (`ReviewResult.next_steps`, filled by the CLI's `_next_steps`) giving the exact goal-loop command when major/moderate findings or fixable citation problems remain. ### Patch-only mode for `andamentum-whetstone`

The `apply-patches` command is the analogue of a standalone "apply review patches to a Word file" script: feed it a .docx and a JSON array of `DocumentPatch` objects (the type defined in `whetstone/models.py`) and it produces a tracked-changes .docx. It is the only remaining caller of `whetstone.docx.finalization.finalize_reviewed_document` and of the text-pattern matcher in `patch_editor.py` — the review pipeline goes through `finalize_annotated_document` instead, because it already knows its coordinates.

```bash
andamentum-whetstone apply-patches draft.docx \
    --patches patches.json \
    -o draft.reviewed.docx \
    --patch-author "Claude" --allow-author-override \
    --patch-report review-summary.md   # optional markdown to prepend
```

`patches.json` is a JSON array; each element is a `DocumentPatch` with `patch_type` ∈ {`text_edit`, `comment`, `document_analysis`}. `text_edit` requires `text_pattern` + `new_text` + `explanation`; `comment` requires `text_pattern` + `comment_text` + `explanation`. This is the foundation for AI-driven draft → review → revise loops where Claude (or another agent) drafts patches separately and then applies them in one tracked-changes pass.

## Layering

- `whetstone` depends on `core` (for `AgentRunner`/`AgentDefinition`, and for `core.models.resolve_model`, which the checklist probe runner calls directly because it constructs its own pydantic-ai `Agent`), on `typeset` for HTML rendering, on `chunker` for section splitting, on `harvest` for source ingestion, on `deep_research` (only when the opt-in novelty check is enabled — `--check-novelty` / `check_novelty=True`; otherwise the import is deferred at runtime, and the `deep_research` types are imported under `TYPE_CHECKING`), on `vision_critique` (only for the goal loop's `--goal-check figures`) and on `llm_judge` (only for the goal loop's `--goal-check judged` — a separate `judge_score` call every round, never the reviewer/editor pass that produced the edit). It MUST NOT depend on `epistemic` or `document_store`.

Public helpers for callers that generate documents: `check_confidentiality(text)` raises `ConfidentialityMarkerError` on a peer-review marker (the tripwire, exported unchanged); `stamp_provenance(docx_path, *, model)` writes the AI-assistance core properties and custom XML part to a `.docx`. `provenance_line(*, model)` is the one-line provenance text those stamps carry (for non-docx outputs). `reviewer_profile(name)` returns a built-in `ReviewerProfile` (`ValueError` on an unknown name) to pass as `reviewer=`.

Docx-reading primitives (importable from `andamentum.whetstone` for `compose.harness`, which MUST NOT import `whetstone.<submodule>`; they are internals, so they are NOT in `__all__`): `body_paragraphs(root)` (the outermost body `<w:p>` elements, review reports excluded), `paragraph_atoms(p)` / `Atom` / `AtomKind` (the one character stream: tracked insertions in, deletions and `w:moveFrom` text out, `mc:Fallback` skipped so a text box is read once, field code out, field result in) and `main_document_part(rels_xml)`. The harness writer reuses the tracked-change surgery through further exports: `document_atoms(paragraphs)` (the whole-document stream, paragraph breaks included), `TextMap` / `AtomSpan` / `SpanEdit` (surgery's `Edit`; `Edit` is the review schema) / `apply_edits` / `EditReport` (span edits as tracked changes; overlapping edits are refused and reported), `next_change_id(root)`, `tracked_paragraph(text, *, author, cid, style_id=None)` (a new paragraph that is one tracked insertion, mark and text; takes `cid` and `cid + 1`), `split_at_boundaries` / `run_bounds` / `translate_span` (comment anchoring on run boundaries) and `XMLElementBuilder` (comment range markers and `w:comment` elements). Nothing else about the docx layer is public; the harness reads and writes with these. `__all__` is the small public surface: the main functions (`review_document`, `run_review`, `run_panel`, `checklist_document`, `run_checklist`, `run_goal_loop`, `open_source`), the three renderers, the input and result types (`Criterion`, `Probe`, `ReviewerProfile`, `GoalSpec`, `FigureRef`, `ReviewResult`, `Finding`, `Edit`, `Quote`, `AuthorQuestion`, `GoalRunResult`), the provenance helpers and the errors (`WhetstoneError`, `ConfidentialityMarkerError`, `DocumentReviewError`). The pipeline package is `whetstone/pipeline/`.

## Design

**Whetstone module** (`andamentum.whetstone`) — structured criterion-cascade review over drafts the user wrote themselves. Public entry: `await review_document(source, *, model)`. Implementation is a pydantic-graph DAG inside `whetstone/pipeline/` — sectionize → extract claims → build document model → run-criteria cascade → verify findings → gap-loop re-grounding → consolidate → 3-node optional novelty check → gate → synthesise → critique-and-revise → optional editor → finalize. Renderers (`render_markdown`, `render_html`, `render_docx`) consume the resulting `ReviewResult` unchanged. **The reviewer reads the text of the document being annotated** (`whetstone/reviewed_document.py`): a `.docx` input is reviewed as the atom projection of its own paragraphs and sectionised by its Word heading styles; any other input is harvested to markdown, written out as a baseline `.docx` FIRST, and then reviewed as *that* file's projection. Either way `Quote.char_start` / `Edit.char_start` are offsets in the whole reviewed document and therefore atom indices in the file being written, so `render_docx` converts them to spans and `whetstone.docx.annotate.apply_annotations` places them with no search, no normalisation and no threshold — a document that does not project to exactly the reviewed text raises `CoordinateError` rather than falling back. (The predecessor searched a converted rendering for the quote text and lost 15 of 43 rewrites on one real manuscript, every miss reporting a nearest match ≥0.97.) The `DocumentPatch` / `text_pattern` path survives ONLY for `andamentum-whetstone apply-patches`, whose input has no coordinates. **Sequential rounds fall out of that same rule and need one parameter, `author`** (`render_docx(..., author=...)`, `--patch-author NAME --allow-author-override` on the CLI, accepted on the review path as well as `apply-patches`): reviewer B's input is A's output, the projection excludes `<w:del>` and includes `<w:ins>`, so B reads the text as Word shows it with A's changes accepted and B editing text A inserted nests as `<w:ins A><w:del B>` — Word's own markup — without a line of round-2 code. There is deliberately no `--round`, no `sequential` mode and no `author=` on the review entry points. Three things make it hold: a prepended review report is bracketed by an `andamentum_review_report_N` bookmark and skipped by `reading.body_paragraphs`, so it is in the file but not in the next round's reading (reports STACK — an earlier report is the earlier reviewer's record; a damaged bookmark fails OPEN); `surgery.next_change_id` and `DocxEditor._next_comment_id` allocate above whatever ids the file already holds, because Word groups a revision by `w:id` and a restart at a fixed base made accepting A's insertion accept B's deletion of it. The same name twice is valid and produces unique ids, but Word groups changes only by author, so the two rounds are indistinguishable in the reviewing pane — pass a different name. Document type routes to one of six pluggable criterion sets via the classifier in `whetstone/_document_type.py`; an unknown type falls back to `GENERAL`. Caller can override the active criterion set with `criteria=[Criterion(...)]` or pass free-text reviewer guidelines via `guidelines_text="..."` (one LLM call decomposes them into a criterion list). Confidentiality-marker tripwire (`whetstone/_confidentiality.py`) refuses to run on peer-review material; `--confirm-own-draft` bypasses. Panel mode (multi-expert simulated peer review) is its own graph in `whetstone/pipeline/panel/` — different shape (N expert biosketches × N independent reviews + 1 synthesis) — invoked via `run_panel` / the `andamentum-whetstone panel` command. Checklist mode is a third graph in `whetstone/pipeline/checklist/` — sectionize → extract claims → build document model → run probes → verify → corroborate → build result, linear, no loops — invoked via `run_checklist` / `checklist_document` / the `andamentum-whetstone checklist` command. Each `Probe` (`checklist/probes.py`) names one defect class and carries a `quota` (`3` = "find the 3 most serious"; `None` = "report every instance, empty list if none"), and one of two shapes: `presence` findings ship a verbatim quote and are anchored by `locate`, `absence` findings ship the missing item plus 2–4 search terms and are DROPPED when any term turns up in the source (conservative by construction — a false "you never state your sample size" is the worst thing this mode can emit). `checklist/bank.py` holds fourteen distinct default probes — a nine-id core, re-skinned academic vs general, plus five per-type additions — routed by the same six document types (`probe_bank_for`, unknown type → `GENERAL_PROBES` with a warning), so a bank is nine to eleven probes; a caller with a house checklist passes `probes=[Probe(...)]` instead. Co-detections are cross-linked (`corroborated_by`) and never merged, the summary is a computed coverage table in bank order where a crashed probe reads `not run` and never `0`, and the confidentiality tripwire runs before any LLM call exactly as in review mode. `document_type` defaults to `"auto"` in the library and on the CLI (one classifier call); pass `"general"` to skip it and keep the cost fixed. Style / readability checks (SMOG, weasel words, passive voice, etc.) are NOT bundled into the review pipeline — use the separate `andamentum.proofread` module or the `andamentum-proofread` command. The older lens-based surfaces (lens-based section-by-section pipeline, `--mode guidelines/custom/panel` flags, `--perspectives`, `--no-challenge`, `--embedding-model`, `--no-proofread`, `--persist-novelty-cache`) were removed; the active code lives under `whetstone/pipeline/`.

**The goal loop** (`whetstone/goal/`, `await run_goal_loop(document, GoalSpec(...), *, model=...)`, `andamentum-whetstone review --goal "..." --goal-check KIND --max-rounds N`) sets a win condition and runs review → edit → re-review until it holds, rather than the fixed single pass every other mode makes. It is a plain bounded loop over functions the review path already has — `review_document`, the same round trip sequential reviewers use (`reviewed_document.carry_forward_edits`, the `_carry_forward` this lifts out of the CLI) — not a second pydantic-graph graph, because a bounded generate-check-retry loop is ordinary control flow under `agentic_dialect` law 5/9, and the one genuinely stateful step is `review_document` itself, called once per round. Four check kinds, chosen by `--goal-check`: `judged` (default) sends `--goal`'s text to `llm_judge.judge_score` as one criterion, in a separate call every round — never the pass that wrote the edit; `structure` reads the round's own `ReviewResult.findings` and is satisfied when the *active* review criteria (whatever `--reviewer`/`--criteria` already selected) raise nothing major or moderate — pair it with `--reviewer reader` for "the flow is correct"; `citations` (`goal/references.py`) runs the same checker as `andamentum-references` (`andamentum.references`, every citation style, with the Word file's superscript/field/note hints) BEFORE each round's review, with `lookup=False` (an edit cannot change what Crossref finds) and the loop's own model for what the text leaves open; its problems reach the round's editor through `review_document(..., extra_findings=...)` — answered beside the review's own findings and listed after them in the result, never reviewed, verified or consolidated — and the goal holds when the checker finds no problem and leaves no candidate unjudged; never whether a citation says what the sentence claims. The simpler scan it replaced (`goal/citations.py`) was deleted: two citation checks would disagree about one document; `figures` (`goal/figures.py`) is the one genuinely new, narrowly-scoped piece — the caller names each figure explicitly (`--goal-figure "Figure 1=fig1.png"`, `--figure-model`), a regex locates its caption and the sentences that mention it (`locate_figure_mentions`), and `vision_critique.critique_figure`'s existing `context`/`schema` parameters carry that text alongside the image; nothing inside `vision_critique` changes, and whetstone does not discover embedded images or associate a caption on its own. A goal counts as met only once its check passes twice in a row, confirming the next round's ordinary edits (which may touch criteria unrelated to the goal) did not undo it — the satisfying round's own edits are then discarded, and when the goal already holds with nothing left to edit, the same text is reviewed again for that second confirmation rather than reading "nothing to change" as stalling. The loop never raises on non-convergence: it always returns a typed `GoalRunResult` (`goal_met`, `stopped_reason` ∈ `{goal_met, no_progress, cap_reached, unresolvable}`, every round's full `ReviewResult`), and a non-`goal_met` stop appends one `AuthorQuestion` naming what it could not settle — the first real producer of a schema field that has existed since Phase 1 but that nothing populated before. `no_progress` covers a round with no edits (only when the goal is not yet met — see above), edits with no net effect on the text, or the draft alternating between two prior states (checked against the last two rounds, not only the immediately preceding one); `unresolvable` is checked once, before spending any round, for a check that cannot be evaluated at all (for `citations`, no reference list and no citation notes, or a citation style the checker cannot decide; a named figure never mentioned for `figures`) — zero rounds run, zero calls made. The CLI maps a non-`goal_met` stop to exit code 1, distinct from exit 4 (the pipeline itself crashed): the output is still written and still real, the code only says the loop did not reach what was asked. `--goal` takes exactly one reviewer (no reconciling several reviewers' findings every round) and runs the editor every round, so `--no-editor` is refused with it.

## Decision model for the document type

`classify(..., decision_model=None)` in `_document_type.py` (keyword-only, threaded from `run_review` / `review_document` / `run_checklist` / `checklist_document` / `run_goal_loop`; CLI `--decision-model NAME`, opened and checked at the start of the run) asks a local `core.decisions` model one six-way `choice` question (`QUESTION`, options from the same `_TYPE_DESCRIPTIONS` the classifier schema uses) and uses its top choice INSTEAD of the LLM call, which is then not made or counted. Without it the LLM classifier runs exactly as before; the flag is refused under `panel` and with an explicit `--document-type`. `andamentum-references` has the same flag.


## Novelty on deep_research (`--check-novelty`)

`--check-novelty` runs the claim check on `deep_research.run_novelty_check`, the only novelty engine; there is no engine flag. Library: `novelty_research=NoveltyResearch(...)` (sources, store, budget; `None` takes the defaults) on `run_review`, `review_document` and `run_goal_loop`.

- **What it does:** a scholarly-mode research run (OpenAlex, Europe PMC, arXiv; `--novelty-search-depth` is the number of rounds) for the claim, then the review's own language model judges every finding of a work that was read, one call each: the probability that the finding reports what the claim presents as new, and that it is about the same topic. A finding with p >= 0.5 for the first makes the claim not novel; its quote is the evidence (`similar_work[].summary`, `direct` from p >= 0.8). Nothing anticipating, after a healthy search (no source or model failure, no spent budget, at least three works read), is novel with confidence `1 - max p`. Anything else is **undetermined** (`is_novel=None`): the target goes down the existing no-signal path, no finding. No model writes the assessment text; it is built from counts and quotes.
- **`--model` alone is enough.** There is no decision model in the novelty path; `--decision-model` keeps its other job (the document-type question). `--novelty-store PATH` (needs `--check-novelty`) keeps the research store (works and passages) between runs; the default is in memory and nothing is kept; no location is assumed. Credentials come from the environment (`OPENALEX_EMAIL`, `OPENALEX_API_KEY`, `SEMANTIC_SCHOLAR_API_KEY`), never flags.
- **Disclosure:** the claim sentences leave the machine, to the scholarly APIs, and the review model reads the works found; the check stays opt-in and the flag/search split above holds.
- **Sequential:** the targets run one after another over one store (the store has one writer). A crash on one target is recorded on that target's evidence and the others go on.
- `pipeline/novelty.py:_evidence_from_report` normalises the report, so `judge_novelty` and `verdicts_to_findings` are shared. Tests: `pipeline/tests/test_novelty_research.py`, `tests/test_novelty_cli.py`, and the goal-loop pass-through in `tests/test_goal_loop.py`; the check itself is tested over an invented world in `deep_research/tests/test_novelty.py`.
- Not measured: how often the model's p >= 0.5 is right for "anticipates", and how often three works read is enough to call a claim novel; the threshold and the minimum are design constants (`ANTICIPATES_AT`, `MIN_WORKS_ASSESSED`), not calibrated.


Command-line notes: `review`'s flags sit in help groups (input and output, model, what to check, editing, goal loop, advanced); the one-line scope note ("whetstone is for your own drafts") prints on stderr for `review`, `panel` and `checklist` only, after the arguments and the input are accepted; `reviewers --json` prints the reviewer list as JSON; `verify-provenance` on an unreadable file prints only the `error:` line (exit 3).
