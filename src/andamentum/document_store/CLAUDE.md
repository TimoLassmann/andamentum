# andamentum.document_store — notes for Claude

Moved from the root `CLAUDE.md`, word for word. Claude Code loads this file when it reads files in this directory.

## Overview

- `andamentum.document_store` — SQLite + FTS5 + sqlite-vec personal knowledge base with 4-signal Reciprocal Rank Fusion search and LLM metadata extraction. Retrieval is two-stage: fusion ranks **documents** by an RRF sum, then `search` reranks the fused top 50 with a cross-encoder by each document's best passage. `get_chunks` / `get_chunk` expose the **passages** underneath with a stable id, and `select_relevant` lets a caller decide how many results are relevant

## CLI

| Script | What it does | LLM? |
|---|---|---|
| `andamentum-docstore` | Deferred ingestion for the document store: `ingest <db> <file> [--defer]`, `ingest-source <db> <path/URL>` (queue a PDF/DOCX/HTML for conversion), `status <db>` (queue depth), `process-pending <db> [--max-docs N] [--max-seconds T]` (resumable drain; Ctrl-C/SIGTERM pauses cleanly after the current document), `retry-failed <db>` | only for `process-pending` and the non-deferred paths; `--defer`, `status` need no model |

## Public API

**Public API lives in `__init__.py`.** Each sub-module's `__init__.py` defines `__all__` explicitly; everything not listed is internal. `document_store` additionally re-exports from `public.py` — that module is the authoritative public surface for document_store (14 functions: `ingest`, `search`, `get_chunks`, `get_chunk`, `find_by_metadata`, `describe_metadata`, `update_metadata`, `delete`, `restore`, `purge`, `list_deleted`, `repair`, `reembed_document`, `find_duplicates`). The read side is three uniform functions usable by humans and agents alike: `search` (unstructured content recall), `find_by_metadata` (structured query — scalar value = equality, list value = set-membership `IN`, plus `include_content=False` for cheap metadata-only overviews), and `describe_metadata` (schema discovery over the schema-less metadata — returns per-field `FieldProfile` with value distributions, bounded by `max_values`). The store stays domain-agnostic: consumers define their own metadata vocabulary and build their own tools on these primitives rather than the store growing a function per consumer.

## Design

**Document store** is SQLite-first. Databases live in `~/.local/share/document-store/{name}.db` (override with `DOCUMENT_STORE_DIR`; legacy `ANDAMENTUM_DATABASES_DIR` is also honoured). Ingestion is two-phase: document registered immediately (FTS5-searchable), chunks + embeddings written in a background pass that `repair()` can resume after a crash.

**Deferred ingestion** (capture now, enrich later) lets the expensive work be queued and drained on a schedule. `ingest(..., process="defer")` registers + FTS-indexes only — no LLM call — and marks the document `pending_enrich`; `ingest_source(database, path_or_url)` queues a source as `pending_source` for later conversion. Note the asymmetry (measured, `H-a5`): only `ingest` gives immediate keyword-searchability — an `ingest_source` row holds `markdown_content=''`, so it returns zero FTS hits until the drain converts it. **Queued documents are kept out of the RRF fusion and appended below it instead.** A document with no chunks can only ever match one of the four signals, so summing reciprocal ranks across all four reads its missing index as three rejections and buries it; the fusion is therefore restricted to `ingest_status='complete'`, and `search_pending_keyword` retrieves the rest into a labelled tail that occupies at most `limit // 5` slots (`search.py`). Tail results carry the ingestion status as their `match_type` and a `warning` naming the remedy — no new field, and no second vocabulary for a state the queue already names. `pending_source` rows are excluded outright by a `markdown_content != ''` predicate: their only indexed text is a filename-derived title, which BM25's length normalisation ranks top on a title-shaped query while there is nothing behind it. A database with an empty queue ranks exactly as it did before the tail existed. `process_pending(database, ...)` drains the queue (`pending_source` →convert→ `pending_enrich` →enrich→ `complete`), one document at a time, committing each transition as it completes — so a run is **resumable** (call it again), **pausable** (`should_continue` / `max_docs` / `max_seconds`), and loses at most one document's compute on a hard kill. `pending_status()` reports queue depth without touching a model; `retry_failed()` requeues failures (which are recorded on the row in `ingest_status`/`ingest_error`, never silently retried). Conversion is **injected** via `convert_fn`, so the store core never imports `harvest`; `document_store/pipeline.py` is the ONLY place `harvest` is imported and simply pre-fills that parameter — an app may call the core directly with its own converter. Converting *outside* the drain (calling harvest yourself, then `ingest()`) is not checkpointed and re-parses in-flight documents after an interruption. The `repair()` crash-sweep deliberately skips `pending_*` documents so an interactive `search()` never turns into a synchronous drain of the backlog. CLI: `andamentum-docstore ingest --defer | ingest-source | status | process-pending | retry-failed` (SIGINT/SIGTERM pause cleanly). The store owns a drainable queue, not a scheduler — cron/launchd supplies the clock. **Ingest never calls an LLM.** The store persists, chunks and embeds text; it does not author metadata. Per-chunk LLM tagging (`topics`/`people`/`has_decision`/`has_action_item`) was removed — nothing read those fields, and they cost ~93% of ingest wall-time (measured 283s -> 3.5s on the same arXiv paper, an 81x speedup, retrieval unchanged). The metadata vocabulary belongs to consumers, who write it via `ingest(metadata=...)`/`update_metadata()` and query it with `find_by_metadata` (deterministic, no LLM). `extract_document_metadata` remains an opt-in utility if you want a generated title. Consequently `ingest`, `process_pending`, `repair` and `reembed_document` take **no `model` argument** — only `embedding_model`; `search` still takes `model` for query planning, plus `reranker_model` for the rerank. Chunking goes through `andamentum.chunker.extract_units` with `target_max_chars=4000`; the `Unit → Chunk` adapter (`chunker_adapter.py`) recovers full heading-breadcrumb `section_path` values via the chunker's structural API. Search fuses four signals via RRF: FTS5 keyword, chunk embeddings, doc embeddings, and DHP (temporal clustering, see `dhp.py`). Requires Ollama running locally with `embeddinggemma-2:latest` for embeddings.

**Retrieval is two-stage, and `search` runs both stages.** Fusion (`search_unified`, and `DocumentStore.search`, which wraps it) ranks documents by an RRF sum, which is built from ranks: it orders one query's results and nothing more. It has no absolute meaning, two queries' scores are not comparable, and it cannot answer "is result 7 relevant or merely seventh". `search` then reranks the fused top `RERANK_POOL` (50) with the cross-encoder named by its required `reranker_model` argument: each document scores as the best of its matched chunks (at most 3), or, with no matched chunk, a 4000-character window around the first query term. `SearchResult.score` is that relevance, and ties keep the fused order. The queued tail is not reranked and stays below. Measured on the retrieval benchmark (MuSiQue dev, 200 multi-hop questions, embeddinggemma-2, `BAAI/bge-reranker-v2-m3`): all supporting passages in the top 10 for 0.395 of questions without the rerank, 0.505 with it, a +0.11 gain whose 95% interval excludes zero. That benchmark has one short passage per document, so the best-passage rule for long documents is not measured. The tools for a caller's own second look: `get_chunks(database, doc_id=...)` enumerates a document's passages in order and `get_chunk(database, chunk_id=...)` resolves one back later (`chunk_hits.py`); `rerank(query, texts, reranker_model=...)` scores them with a cross-encoder and `select_relevant(scored, min_relevance=..., buffer=...)` decides how many to keep (`reranking.py`). Chunk hits also ride out of `search` on `SearchResult.chunks` for documents the chunk signal matched — accumulated per document rather than collapsed with it, since the chunk signal emits one result per *chunk* and fusion is per *document*; the same document arriving three times would otherwise lose two real passages invisibly.

Four decisions in that design are load-bearing. **The chunk id is `"{doc_id}:{chunk_index}"` — a coordinate, not a content hash.** It survives re-embedding (which rewrites every AUTOINCREMENT row id and leaves positions alone), and it does not survive re-chunking; a caller who must detect that compares `ChunkHit.content`. The row id is deliberately not the public id because it is stable across strictly less. **`search` always reranks, and the fusion never does.** The cost is real: a 0.6B cross-encoder resident in this process for its lifetime, on a memory budget nothing in `ollama ps` accounts for, plus a few seconds per search. It is paid because the rerank was the largest measured retrieval gain. sentence-transformers is therefore a core dependency, so results never depend on which extras are installed. `search_unified` stays a pure fusion call; `tests/test_search_chunk_hits.py` fails if the reranker is wired into it, and `tests/test_search_rerank.py` pins the rerank in `search`. **`min_relevance` and `reranker_model` have no defaults, in `search` too.** A score's scale belongs to one specific model, so a floor calibrated elsewhere is a domain assumption wearing the clothes of a constant — `SUGGESTED_RERANKER_MODEL` is a suggestion no function reads. **The elbow cut and the absolute floor are both required and neither is redundant.** Normalising near-identical noise to [0, 1] manufactures visible structure: measured, 50 near-zero scores produce a confident-looking elbow that keeps a quarter of them, and only the floor excludes that. The elbow also errs generous by up to one item structurally — it finds the *corner*, and an index cannot say whether the corner is the last good item or the first bad one — so a clean five-good-then-thirty-bad curve keeps six. Do not tune that away; the floor removes the extra on evidence.
