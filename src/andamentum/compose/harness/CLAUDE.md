# andamentum.compose.harness — notes for Claude

This is the implementation of the **`andamentum-word`** tool (the public face is `andamentum.word`: `word/api.py` names one async function per job, `word/cli.py` is the command line). `andamentum-compose` is the other tool (a task into a document folder) and does not use the harness. The harness's own `Verb` registry stays internal: the MCP server reads its tools from it, and the word command line is a separate, explicit argparse tree.

Claude Code loads this file when it reads files in this directory. The design notes are kept outside the repository; what the code relies on is stated below. Sections below are written per stage; later stages append to them.

## Layout and layering

`kernel/` (format-neutral types, no `pydantic_graph`), `docx/` (reader, writer, anchors, fields, citations), `literature/`, `draft/` (`draft` into Word: notes in `draft/CLAUDE.md`), `md/`, `checks/`, `bench/`, `spike/`. Nothing outside `andamentum.compose` and `andamentum.word` imports `compose.harness`. `errors.py` holds `WordError` (base of every error the Word tools raise on purpose), `WordUsageError` (exit 2) and `WordInputError` (exit 3); the harness's own errors derive from them.

Kernel conventions that later code must keep:

- Every op carries an `op: Literal[...]` tag; `Operation` is a union discriminated on it. Ops and `Transaction` are frozen; all models forbid extra fields.
- `DocumentView.sections()` starts a new section at every heading of any level; the heading paragraph is not in its id list; paragraphs before the first heading form a section with heading `""`, only when there are any.
- `Move` and `Unbind` are declared in `kernel/ops.py` but the docx writer raises `NotImplementedError` for them.

## Docx reading: reuse decision

**Decision: reuse whetstone's atom stream through new public exports; no `docx_core` module.**

the leaf module `andamentum.docx_edit` already answers the one hard question, "what text does this paragraph have, and which XML node is each character": `andamentum.docx_edit.atoms.paragraph_atoms` descends into everything except `w:del`, so tracked insertions, content controls, hyperlinks and field results are in the text and field code (`w:instrText`) and deleted text are not. `andamentum.docx_edit.body.body_paragraphs` decides which `<w:p>` are body paragraphs (tables in, text boxes not counted twice, a prepended whetstone review report out). The harness writer must address the same characters `andamentum.docx_edit.surgery` edits, so both ends have to share this one definition; a second walker would drift.

The exports added to `whetstone/__init__.py` (documented in `whetstone/CLAUDE.md`): `Atom`, `AtomKind`, `paragraph_atoms`, `body_paragraphs`, `main_document_part`. `compose` is forbidden from importing `whetstone.<submodule>` by the compose conformance test, so a public export is the only legal route.

Why not a neutral `andamentum/docx_core/`: moving `atoms.py` and `reading.py` there would rewrite imports in about a dozen whetstone modules and their tests while the writer stage edits `whetstone/docx/surgery` concurrently, for no gain over five exports. If a third consumer appears, moving them is a mechanical change then. Everything the reader needs beyond these primitives (comments parts, fields, content controls, custom XML, styles) is not whetstone's business and lives in `docx/`: `ooxml.py` (names, relationships), `anchors.py`, `fields.py`, `reader.py`.

The reader does import `andamentum.whetstone` (the package, which pulls in pydantic-ai) for four tiny functions; accepted, since compose already depends on whetstone.

## Reader rules (`docx/reader.py`)

- `open_docx(path) -> DocumentView`; `parse_docx(path) -> ParsedDocx` also returns the root, the body `<w:p>` elements and their atoms, index-aligned with `view.paragraphs`, for the writer. Never modifies the file; XML is parsed without entity expansion or network.
- **Paragraph ids:** `p<index>` (position among body paragraphs) plus `-<w14:paraId>` when Word recorded one, e.g. `p6-10000007`. A pure function of the file, so identical across re-opens. **Stability rule:** an id is valid only against the file it was read from; a file that gained or lost a paragraph renumbers those after it (and LibreOffice rewrites every `w14:paraId`). Never persist a paragraph id across edits; persist anchor ids and text fingerprints instead.
- Paragraph `text` is the atom projection: tracked insertions in, deletions and `w:moveFrom` text out, `mc:Fallback` skipped (a text box is read once), field code out, field result in, `w:br` / `w:tab` as one space. All offsets (anchors, fields, comments) index this text.
- `Paragraph.style` is the style's display name (`heading 1`, `Title`), falling back to the style id, then `Normal`. `heading_level` comes from a direct `w:outlineLvl`, else the style chain (`heading N` name, outline level, `basedOn`). Title is not a heading.
- **Anchors:** a `w:sdt` with `w:tag` `am:<id>`. The kind is read from `w:alias` (`claim|number|figure|span`; absent or unknown reads as `span`) — the spec fixed only the tag, so the writer MUST set the alias. A block-level control wrapping whole paragraphs is reported on its first paragraph, covering all of it. Other content controls are ignored.
- **Project id:** a custom XML part whose root is in `urn:andamentum:harness` with a `projectId` attribute (`anchors.project_id_part_xml` builds it; a `<projectId>` child is read too).
- **Fields:** complex fields (`fldChar` begin/separate/end, instruction pieces concatenated, nesting and cross-paragraph spans handled) and `w:fldSimple`; order is by start position, outer before inner. A field in a deleted run is ignored. `fields.classify_field` maps an instruction to `(kind, manager, data)`: Zotero (`ZOTERO_ITEM CSL_CITATION`, `ZOTERO_BIBL`), Mendeley (`ADDIN CSL_CITATION`, `Mendeley Bibliography`), EndNote (`EN.CITE` XML in the instruction; `EN.CITE.DATA` is `kind="other"` so a citation is not counted twice; `EN.REFLIST`), Word `REF`/`PAGEREF`/`NOTEREF`/`SEQ` (`crossref`, `data["target"]` is the bookmark or SEQ series; for REF/PAGEREF/NOTEREF the reader also sets `data["target_exists"]` (bool) from the document's `w:bookmarkStart` names, SEQ gets none), `CITATION`/`BIBLIOGRAPHY`. A payload that does not parse still yields a token with `data={"parse_error": ..., "raw": ...}`; the crossrefs check reports it.
- A field spanning paragraphs (the bibliography) is reported on its first paragraph: `end` is that paragraph's length and `display` is the whole result joined by newline.
- **Plain-text citations** are `FieldToken(kind="citation", manager="none")` from `andamentum.references.scan` over the view text (sources `brackets`, `parenthetical`, `narrative`, `key`, and `superscript` from `w:vertAlign`); `(3)` and glued digits are left out as too ambiguous without the whole-document style decision. Spans inside a manager field are not reported twice; a candidate crossing a paragraph break is dropped. `data` has `source`, `numbers`, `works`, `keys`.
- **Comments:** `comments.xml` plus `commentsExtended.xml` (`w15:paraIdParent` gives `parent_id`; `w15:done` gives `resolved`). `commentsIds.xml` is not read (nothing needs the durable id). A comment's range is `commentRangeStart/End` (a range crossing paragraphs is cut at the end of the first); a bare `commentReference` is a point. A comment with no anchor in the body has `paragraph_id == ""` and a zero range.

## M0 spike (`spike/`)

`make.py` builds synthetic `.docx` from raw WordprocessingML (`build_docx`, and helpers `run`, `paragraph`, `complex_field`, `content_control`, `comment_part`, ...; the reader tests use it too) because python-docx cannot write controls, fields, threaded comments or custom parts. `make_spike_docx` is the "SaltLog pilot" document. `probe.py` reads a file with the harness reader and compares it with what was written; `survival.py` runs python-docx, LibreOffice headless (private profile dir in the work dir, never the home) and whetstone `open_source`. CLI: `uv run python -m andamentum.compose.harness.spike {make PATH | probe FILE [--json] | survival --workdir DIR [--report FILE]}`.

Measured (this machine, synthetic file): every item survives python-docx and LibreOffice; LibreOffice renumbers comment and tracked-change ids, rewrites `w14:paraId`, and drops `commentsIds.xml`. Word desktop and Word on the web are untested and need the user (six manual edits made inside Word: type into, delete, and paste over a control, a comment reply, a Zotero refresh, and a save in Word on the web); until then the content-control design is unproven against real Word edits. Fallback if Word breaks controls: bookmarks plus text fingerprints with re-anchoring (not built: a bookmark per anchor plus a text fingerprint, re-anchored by search when the bookmark is gone).

## Writer rules (`docx/writer.py`)

- `DocxAdapter.apply(view, txn, *, output)` reads `view.path` again, refuses a stale view (`ValueError`) and an `output` equal to the input, applies the ops to the parsed XML, writes a new package, then **re-opens the output with the reader and checks it**: every edited paragraph reads as planned, every other paragraph has the same text and the same XML bytes, new comments / replies / anchors read back where requested, python-docx opens it. Any failure raises `DocxApplyError` and deletes the output. Package parts the transaction does not need are copied through byte for byte; only `document.xml`, the comment parts, rels and content types are rewritten.
- **Reuse:** Replace/Insert/Delete are whetstone's surgery (`apply_edits`, exported with `SpanEdit`, `TextMap`, `AtomSpan`, `document_atoms`, `next_change_id`, `split_at_boundaries`, `run_bounds`, `translate_span`, `XMLElementBuilder`). `SpanEdit` is surgery's `Edit`; `whetstone.Edit` is the review schema. Replace is diffed at word level inside the range, so a one-word change marks one word. The tracked inserted paragraph is whetstone's `tracked_paragraph` (one tracked insertion, mark and text, same timestamp spelling as every other revision); the only XML the harness builds itself is what whetstone has no equivalent for: the content control, the comment paragraphs with `w14:paraId`, `commentsExtended` entries.
- **Order:** edits first, then new paragraphs, then comments and binds (their ranges are translated by the edits' exact length change), then replies. Comments are placed before binds so a comment on the same range ends up outside the control.
- **Refusals** (listed in `ApplyResult.refused`, the rest of the transaction still applies): `expect` mismatch, unknown paragraph/comment/style, range past the paragraph end, newline in an edit (use `InsertParagraph`), no text character next to the range to attach an insertion (an empty paragraph), overlap with another edit, a comment range emptied by a delete in the same transaction, a `Bind` that overlaps an edit or another bind, duplicates an anchor id, cuts a field, or crosses a tracked-change/hyperlink boundary, a `Reply` to a comment with no body anchor. Refusal is decided before a run is split, so a refused op leaves its paragraph byte-identical.
- **Fields are never edited inside** (`docx/field_spans.py` locates every field result in view coordinates). `Replace` / `Delete` touching a result and an `Insert` strictly inside one are refused. An `Insert` at the edge of a field result, hyperlink, content control or `fldSimple` is moved just outside it after surgery (the text projection is unchanged) and takes the run properties of the nearest text outside, so it does not vanish on a refresh and does not inherit superscript or link formatting. A `CommentOp` touching a result is widened to the whole result and its markers go around the field's first and last run; a field that spans paragraphs reads back cut at the end of its first paragraph. A `Bind` that cuts a result is refused; one that covers it wraps the whole field. Tests assert nothing sits between a `separate` and an `end` `fldChar`.
- `Reply` joins the thread's root (a reply to a reply is a reply to the root) and goes after the thread's last member; parent and reply get `commentsExtended` entries (`w15:paraIdParent`), and the part is created when a transaction holds a reply. A reply to a comment created in the same transaction is not supported (its id is assigned at apply time).
- `Bind` writes `w:alias` = kind, `w:tag` = `am:<id>`, `w:id`, `w15:appearance` hidden, no lock and no type element (a rich-text control; locked or plain-text controls would delete or flatten the author's formatting). Whether Word keeps it through a person editing inside is the M0 question that is still open.
- `InsertParagraph` has no `Normal` pStyle unless the style is named; it does not copy the reference paragraph's style (a paragraph added after a heading is not a heading). `Move` and `Unbind` raise `NotImplementedError`.
- `DocxAdapter.write_project_id(path, *, project_id, output)` adds the `urn:andamentum:harness` custom XML part to a copy; an id already in the file must match.
- Not done: `commentsIds.xml` is not extended for new comments; an insertion into a paragraph with no text is refused; whetstone stamps tracked changes with a naive local time while the harness stamps comments and inserted paragraphs in UTC (same instant, different spelling).

## Kernel storage, registries and the markdown adapter

- **`ProjectStore`** (`kernel/store.py`): the folder `state/` in the output folder (the folder that holds the written copy), or an explicit `project` in the params (`project_dir(out, project)` in `project.py`); nothing is ever kept beside the input. `project.yaml` (id, created, `schema_version` 1; an unknown version raises), optional `checks.yaml` (`structure:` and `models:` sections), `events.jsonl` (append-only, one JSON object per line, a corrupt line raises on read), `cache/` and `view/`. `init(docx, *, project_id=None)` is idempotent; an existing project keeps its id and a different one raises. The id is written into the document only by `DocxAdapter.write_project_id`.
- **Caches:** `cache/checks/<key>.json` holds a deterministic check's diagnostics (key = check id, check `version` (a required attribute of every check), hash of the whole `DocumentView` minus its path (styles, heading levels, field data, anchors, comments) and of the project `checks.yaml`); `cache/http/<key>.json` holds HTTP answers (`HttpCache`, hit and miss counters; read through `ProjectCache`, which fetches an answer again after `ANSWER_MAX_AGE`, 7 days, because a work checked once may be retracted later); model-judged checks keep their own namespaces (`numbers`, `needs_citation`) keyed by the text asked plus the result files' digests or the model id. Only checks with no `needs` are cached whole ; network and model checks run every time and rely on the HTTP cache and their own namespaces.
- **Shadow git:** `snapshot_view(view, *, message)` writes `view/document.txt` and `view/paragraphs.json` and commits, one commit per call even when nothing changed. git runs with global and system config switched off, hooks disabled and the author set per command, so nothing outside the project folder is read or written.
- **Promotion policy:** `effective_tier(check, *, precision)` keeps a model-judged check's declared tier only when a measured precision of at least `PROMOTE_AT` (0.9) is on record; otherwise it reports at tier 2 (advisory). A check is model-judged when it needs `model` or `decision_model`. Precisions come from `<project>/precision.json` (`{check id: {"precision": x}}`). The check verb rewrites each diagnostic's tier to the effective one.
- **Models:** `ModelRegistry`/`ModelEntry` (`kernel/models.py`) read the `models:` section of `checks.yaml`: role, `kind` (`llm` or `decision`), id, digest. `--decision-model` is opened and checked (`DecisionModel.open`: Ollama version, capability, digest) at the start of the run; `run_check(..., decision_handle=)` takes a ready handle (tests).
- **Verbs:** `kernel/verbs.py` builds argparse subcommands from a params model (`json_schema_extra={"positional": True}` makes a positional; `bool` a switch, `list[X]` a repeated flag, `Literal` choices). Modules listed in `VERB_MODULES` expose `VERBS`; `load_builtin_verbs()` registers what is missing, so it can be called again after a test cleared the registry.
- **`CheckContext`** carries `store`, `offline`, `models` (role to model id: `model`, `decision_model`), `results_dir`, `http` (the run's one cached `ReferenceHttp`, None when offline), `decision_model` (the checked `DecisionModel` handle) and `stats` (`RunStats`: network calls, model calls, tokens).
- **Markdown adapter** (`md/adapter.py`) over `compose.bundle`: ids are `sNN:h` (the section heading, level 1) and `sNN:0`, `sNN:1`, ... for body blocks split at blank lines. Insert, Replace, Delete and InsertParagraph work (a heading Replace renames the section); Bind, CommentOp, Reply, Move and Unbind raise `NotImplementedError` (markdown has no comments or controls). `apply` copies the bundle to an empty `output`, edits the copy and re-reads it; it refuses a bundle that changed since the view was opened.

## Checks (`checks/`)

Each check registers an instance at import; `harness/check.py` imports them all. Every module docstring lists its coverage limits; the short form:

| id | tier | needs | what it does | main limits |
|---|---|---|---|---|
| `crossrefs` | 0 | none | REF/PAGEREF/NOTEREF target bookmark exists (`target_exists`), citation fields parse (no `parse_error`), a bibliography field when citations exist, "Figure N"/"Table N" mentions have captions | first number of "Figures 1 and 2" only; plain-text citations not looked at |
| `statistics` | 0 | none | recompute p for t, F, chi-square, r, z (rounded statistic gives a range; one-tailed accepted when stated); GRIM only when n and item count are stated | no regression coefficients, tables, corrections, split sentences |
| `abstract_body` | 0 | none | numbers in the abstract must occur in the body | numbers only in tables read as missing |
| `structure` | 0 | none | limits and required sections from the project `checks.yaml` (`structure:`); no config, no output | one config per project folder |
| `citations` | 0 | network | existence and metadata of cited works (fields and plain reference entries; two-stage resolve), retraction notices (error) and other notices (warning), URL health | unresolved is a warning, never an error; hyperlink targets that differ from their display text are not read |
| `numbers` | 1 | results, model | a model extracts numeric claims per paragraph, code matches them against csv/tsv/json result files at the written precision | derived values not found; 80 paragraphs per run |
| `needs_citation` | 1 | decision_model | uncited sentences the decision model rates yes (probability at least 0.5), as info | advisory (tier 2) unless `precision.json` holds a precision for it; its answers are cached by digest and question hash |

Diagnostics carry `data["kind"]` where one check reports several things (`crossrefs`: `dangling_target`, `no_target`, `unparseable_field`, `no_bibliography`, `missing_caption`; `citations`: `unresolved`, `details_differ`, `unlisted` (a plain-text author-year citation no reference-list entry names; warning), `retraction`, `expression_of_concern`, `correction`, `url`, `lookup_failed`; a retraction lookup that fails is its own per-work `lookup_failed` warning, never a clean report); the benchmark maps defect kinds through it.

`citations` network behaviour: one `ReferenceHttp` per run, cached in the project (`cache/http/`), polite user agent, `mailto` only with `--mailto`. A work cited by a field and listed as an entry is looked up once and reported at each place. Lookups are sequential. Plain entries go through `references.resolve_entry`; fields through `resolve_cited_work` (a field with no authors does not have its record's first author held against it).

## The `check` verb (`check.py`)

`andamentum-word check FILE.docx -o DIR [--results DIR] [--checks ids] [--model M] [--decision-model M] [--mailto ADDR] [--offline]` (the params model also has `out` as the copy's path, `report` and `project`; the command line fills them from `-o DIR`: `DIR/<stem>.checked.docx`, `.md`/`.json` beside it, `DIR/state/`). Default selection is every registered check whose needs the flags meet (so `numbers` needs `--results` and `--model`, `needs_citation` needs `--decision-model`, network checks drop out under `--offline`); an explicitly named check with an unmet need is a usage error. The commented copy `<stem>.checked.docx` carries one comment per located diagnostic signed "andamentum check"; the input is never opened for writing, and `--out` equal to the input is refused. The copy carries the project id (added through `write_project_id`). Report: `<stem>.checked.md` and `.json` (counts, checks run, from cache, skipped with reasons, network calls, HTTP cache hits, tokens, time). Exit 0 no errors, 1 errors found, 2 usage error (the command line maps 3 input unreadable, 4 crash). Events `transaction` and `check_run` go to `events.jsonl`; the text view is committed to the shadow git. `run_check(params, *, transport=None, url_check=None)` is the programmatic entry the benchmark uses.

## Benchmark (`bench/`)

`planted.py` generates the synthetic set (14 files, 4 clean, 50 defects, eight kinds each at least 5); `fixture_http.py` serves the recorded Crossref and URL fixtures as an `httpx` transport (an uncovered request raises `FixtureMissing`); `run.py` scores the harness arm against an optional one-call baseline arm (`--baseline-model M`, paragraph-numbered text, the model labels findings with a kind): per-kind recall, false positives on clean and on defective files, tokens, seconds, network calls.

    uv run python -m andamentum.compose.harness.bench.run --offline --seed 0
    uv run python -m andamentum.compose.harness.bench.run --live --seed 0 --baseline-model M --mailto ADDR

Scoring: a defect is found when a diagnostic of its kind lies in one of its paragraphs; error and warning diagnostics are findings, info is not; a finding matching no planted (kind, paragraph) is a false positive. **Measured offline** (seeds 0, 1, 2, 3 and 12345, identical totals): 50 of 50 defects found, every kind 100%, 0 false positives on clean files and 0 on defective ones, 60 findings (a bad DOI is reported at the in-text citation and at the entry), 142 fixture-served network calls at seed 0, about 1.5 s. `tests/test_bench_run.py` sets floors under that: overall recall at least 0.9, each kind at least 0.8, no false positive on clean files, at most 2 elsewhere; a control (crossrefs only) shows the scoring fails when a check is missing. The generator and the checks were written against the same spec, so 100% says the harness finds what it was built to find on this set, not how it does on real manuscripts; the live mode and the baseline arm are the honest comparison and have not been run (they cost network and tokens).

## Citations and the literature layer

**Operations** (`kernel/ops.py`): `InsertCitation(paragraph_id, at, items)` with `CitationItem(csl, locator, prefix, suffix, uri)`, and the document-level `UpdateBibliography()`. `at` is verbatim: no space is added around the citation text. `uri` is set only for a work that came from Zotero. The markdown adapter raises `NotImplementedError` for both. **EndNote fields are read only; writing them is out of scope.**

**Writer** (`docx/citations.py`, wired into `DocxAdapter.apply`): `expand_citations` rewrites the two ops into kernel ops before the writer plans anything, so position handling, field-edge hoisting and refusals are the existing ones; `ApplyResult.applied` still counts the caller's ops (`Expansion.origin` maps each derived op back).
- *Mode:* a Zotero field when the document has Zotero fields or any item has a `uri`; plain text otherwise.
- *Zotero citation:* an `Insert` of the display text; once surgery has written it (the run it reports in `EditReport.insertions`), that run is replaced inside the same `w:ins` by `begin`, `ADDIN ZOTERO_ITEM CSL_CITATION {json}`, `separate`, the result run, `end`, all with the run's properties. `citationItems[].itemData` is the CSL; `uris` only for an item with a `uri`. The reader must see a well-formed new zotero citation token with the display text, or `_verify_citations` raises.
- *Zotero bibliography:* an existing `ADDIN ZOTERO_BIBL` field gets the missing entries as one tracked `w:ins` just before its `end` run (a `w:br` before each entry); it is a hand-made `SpanEdit` in `applied_edits` (never given to surgery) so later spans translate past it. Entries are only added, never removed or re-sorted; Zotero reflows on the next refresh. With no field: a "References" heading (unless the document has one; `heading 1` only if the style exists) and a tracked paragraph holding the new field.
- *Plain:* the citation is an `Insert`; the reference list is the paragraphs after a "References"/"Bibliography" heading. Missing entries become tracked `InsertParagraph`s: alphabetical when the existing list is, else at the end; a numeric list continues its numbers (an entry already listed keeps its own). A work counts as listed when its DOI or normalised title is in an entry. Plain works are known only from the transaction's `InsertCitation` items, so `UpdateBibliography` lists those; existing plain citations carry no CSL.
- *Style* (`kernel/csl.py`): `detect_style` reads the document's existing citation displays (numeric or author-year, brackets, comma before the year, `&`); default author-year without comma. Not a CSL engine: no year suffixes (`2020a`), no italics, no superscript numbers. Numeric numbers follow order of addition, so a citation inserted before an earlier one leaves the list out of first-citation order, which the `citations` check reports.
- Citation entries use a generic author-year (APA-like) or numeric (Vancouver-like) plain-text form.

**Literature** (`literature/`, async, no model): `read_library` (CSL JSON list or `{"items": [...]}`; BibTeX with braces, accents, `and` names, `--` pages; `@string` macros and `#` concatenation are not handled; an entry with neither title nor DOI is an error), `ZoteroLibrary` (the local API at `http://127.0.0.1:23119/api/`, **read only: it has no write method**; reads the whole library once with `include=data,csljson`, skips attachments/notes, raises over `max_items`; an item's `uri` is its real one (the CSL id when it is an item URI, else built from the entry's synced `library` id and key, else a zotero.org link); a never-synced local item has `uri=None` and its citation carries only `itemData`, never an invented URI), `search_crossref` (through `ReferenceHttp.crossref`, the package's only Crossref client; sends only the query text), `find_works(query, sources=Sources(library, zotero, crossref), limit)` (library, then Zotero, then Crossref only when fewer than `limit` were found; one work once; a source that cannot answer raises `LiteratureError`, never an empty list) and `resolve(work, http=)`: `resolve_cited_work` (DOI fetch or title search, title must be the cited one) then `lookup_retraction`. A `VerifiedWork` may be cited (non-retraction notices ride along); an `Unverified` (`not_found`, `details_differ`, `retracted`, `unchecked`) never is, and its `reason` is the author question. `unchecked` (service down, nothing to look up, no DOI to check retraction against) is never a pass. Local ranking (`literature/search.py`) is content-word overlap, at least two of the query's words; Crossref results go through the same ranking, so a record sharing fewer than two words is dropped. Measured: nothing; tests use invented works and a mock Crossref.

## The verbs and the MCP server

Every verb is a `Verb` (name, one-line summary with an example, params model, handler returning an exit code) registered through `VERB_MODULES` in `kernel/verbs.py`; the CLI subcommands, the `--help` lines and the MCP tools all come from that registry, so a verb is added in one place. Each verb never edits its input and writes a copy.

- `check` (above), `draft` (`draft/verb.py`: the Word path in `draft/`, `--into` optional; needs only the drafter and judge models. The `andamentum-word draft` command line takes one required `--model` for both, has no `--max-rounds` (2 revise rounds, `WORD_ROUNDS`) and one research flag, `--research {auto,web,scholarly,both}` (`auto`: the genre chooses; `word/cli.py` maps it to `research=True, research_mode=None|MODE`); `DraftParams` (and so the MCP `draft` tool) and `andamentum.word.draft_document` keep `drafter`, `judge`, `max_rounds` and `research_mode`. The old bundle destination is `andamentum-compose write`), `bind-numbers` and `refresh` (`bindings/CLAUDE.md`), `respond` (`respond/CLAUDE.md`), `find-citation` and `insert-citation` (`literature/verbs.py`: both verify through `resolve` and never cite an unverified work; `insert-citation` writes nothing and exits 1 if any work fails; `--at` is a character offset and the citation goes in verbatim), `paragraphs` (`word/api.py` `list_paragraphs`: read-only, lists the paragraph ids `insert-citation` takes), `mcp` (`mcp_server.py`).
- `project.py` is the one place a document's project folder is found (`project_dir(out, project)`: `project`, else `state/` beside the output copy) and the one place a copy is written (`write_copy`, which stamps the project id). `check`, `respond`, `bind-numbers`, `refresh`, `insert-citation`, `draft` and MCP `apply_edits` all use them, so a run into the same output folder keeps the ledger, the event log and the snapshots of the earlier run (`refresh` finds the bindings `bind-numbers` wrote there). The params models take `out` as the path of the copy (required; the word command line derives it from `-o DIR`). **No verb writes over a file:** `check`, `respond`, `refresh`, `bind-numbers` and `insert-citation` call `project.refuse_taken(written_files(out, report))` (the copy and its `.md` / `.json` report; `insert-citation` writes no report) before anything is written, `state/` included, and raise their usage error (exit 2) naming each existing file; a copy from an earlier run may hold edits made in Word. MCP `apply_edits` refuses an existing `out` the same way; `draft` has its own check with the same rule. A rerun into the same folder therefore first removes the earlier copy and report (`tests/_helpers.py::clear_outputs`); `tests/test_no_overwrite.py` covers every verb.
- The writer plans citations twice when it must: an `InsertCitation` it refuses is dropped and the bibliography is planned again, so a refused citation leaves no reference-list entry. `respond` refuses a rewrite that types a new citation (`respond/edits.py`), and refuses to run when `response-letter.docx` or `.md` already exist in the output folder.
- **`respond` triage with a decision model** (`respond/triage.py`, `triage_with_decision`): `--decision-model` is opened and checked at the start (`run_respond(..., decision_handle=)` takes a ready handle); `TRIAGE_QUESTION` (a `choice` over `edit`/`answer`/`author`/`done` with a description each) is asked instead of the triage call and its top category is the category. `author` and `done` are templated, with no language-model call: `templated_triage` writes the reason (`author`) or finds the best matching sentence of the document by shared words, at least `MIN_SHARED_WORDS` (`done`; none found is the existing demotion to `author`). `edit` and `answer` still call the language model with the category fixed, for the quote and the text. `DecisionRecord` in the report says the choice, its probability and whether the triage call was saved. Unmeasured: how often the templated `done` evidence is the right passage.
- `literature/access.py` (`open_literature`) builds the `Sources` and the cached `ReferenceHttp` that `write`, `find-citation` and `insert-citation` share. Verifying a work always asks Crossref, so `write --offline` drafts without literature.
- **MCP server** (`andamentum-word mcp`, stdio, the `mcp` SDK): nine tools. `open_document`, `show_section` and `apply_edits` are native; `check`, `draft`, `refresh`, `respond`, `find_citation` and `insert_citation` run the verb of the same name (`-` for `_`) with its params model as the input schema, looked up in the registry at call time. Every call writes to a copy: `apply_edits` refuses `out` equal to the input and refuses citation operations (a work enters a document only through `insert_citation`, which verifies it), a verb tool refuses an `out` equal to an input `.docx`, and the SHA-256 of every input `.docx` is compared before and after a verb call (a change fails loudly). Exit 2 and crashes are tool errors; 1 and 4 are results. A tool call names the copy with `out` (a `.docx` path); `state/` goes beside it unless `project` is given. The resource `compose://report/last` is the last report. Handler stdout and stderr are captured so they cannot corrupt the protocol stream. Tests use the SDK's in-memory client plus one real stdio subprocess.
- Guide: `docs/word.md`; `tests/test_example_project.py` parses every `andamentum-word` command in it against the real parser, and `tests/test_example_end_to_end.py` runs draft, refresh, respond and MCP on the SaltLog example project (`examples/`).

## Pitfalls

- A `ReferenceHttp` built on fixture `.example` hosts needs a URL-safety predicate without DNS (`scheme_only_url_check`); production keeps `core.url_safety.is_safe_url`.
- `httpx` client event hooks on an `AsyncClient` must be `async def`.
- Tests are offline: `compose/conftest.py` makes the real httpx transports raise (except for tests with a live marker: `compose_eval`, `ollama`, `cloud`, `live_provider`); every other test injects a `MockTransport` or the fixtures. `references/tests/` has the same fixture and needs its `__init__.py`, or two `conftest` modules collide.
- Dialect conformance (strict) forbids `dict[str, Any]` anywhere in compose; use pydantic models or `dict[str, object]`.
- Do not persist a paragraph id across edits (see the reader's stability rule).
