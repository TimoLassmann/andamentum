andamentum sub-module

andamentum.llm_judge

A dead-simple LLM-as-judge primitive: score one output, or compare two — with a confidence and an honest doubt signal, on a fast single judge or a sequential panel.

Leaf module · CLI andamentum-llm-judge · depends only on core + pydantic-ai + stdlib · reference for maintainers and callers

Two async functions — judge_score and judge_compare — each with one call shape that switches between a fast single judge and a consensus panel purely through the type of the model argument. Verdicts come from a verbalized distribution the model fills, not a bare confidence number; confidence and doubt are derived from that distribution deterministically, and a panel is used only as an agreement gate — never to fabricate a smarter averaged answer.

What it is, and when to reach for it

llm_judge is the small, general primitive for the recurring question “is this model output any good, and how sure are we?” It does two things and nothing else:

  • Score one output against a set of criteria (judge_score).
  • Compare two outputs and say which is better (judge_compare).

Reach for it when you need a quick, structured quality read on generated text — ranking candidates, gating a pipeline step, building a preference signal, or flagging outputs that deserve a human second look. It is deliberately domain-agnostic: the default criteria apply to almost any task, and a caller with a specific domain passes their own criteria rather than the module growing domain-specific lists.

It is shaped like andamentum.vision_critique: single async entry points, bounded flat-ish pydantic schemas, no pydantic-graph and no graph.py. There is nothing to route between — one call, or a strictly sequential fan-out with a deterministic roll-up — so a graph engine would be pure ceremony. The module is still fully dialect-conforming without one.

The design is grounded in two prior experiments in this repo: experiments/dirichlet_confidence/ (pointwise scoring on SciFact) and experiments/pairwise_judge/ (pairwise comparison on JudgeBench). Every non-obvious decision below traces back to a finding from one of them.

Not to be confused with

This is a general-purpose judge, distinct from epistemic.judgment_signal (evidence-vs-claim verdicts) and whetstone's per-criterion review head. Those overlap conceptually but are separate pipelines with their own concerns; llm_judge does not touch or depend on either.

The two functions

score one output

judge_score

Scores output against each criterion independently — one verbalized distribution per criterion — then rolls the criteria up into one overall verdict of meets partial fails.

compare two outputs

judge_compare

Decides which of output_a / output_b is better. winner is always a value — a b tie — and both presentation orders are always run to defuse position bias.

Signatures

async def judge_score(
    output: str, *,
    criteria: list[Criterion] | None = None,
    context: str | None = None,
    model: str | Sequence[str],
) -> ScoreResult

async def judge_compare(
    output_a: str, output_b: str, *,
    criteria: list[Criterion] | None = None,
    context: str | None = None,
    model: str | Sequence[str],
) -> CompareResult

model is keyword-only and has no default — the whole package's rule. context is the task or prompt the output was answering; it is optional, but when present it is woven into the prompt (it changes the prompt shape rather than being folded in as a sometimes-empty field). criteria=None falls back to DEFAULT_CRITERIA.

Usage — fast single judge

from andamentum.llm_judge import judge_score

result = await judge_score(
    "Paris is the capital of France.",
    context="What is the capital of France?",
    model="anthropic:claude-haiku-4-5",   # a str -> fast path
)
print(result.overall, result.confidence, result.doubt)
# meets 0.94 0.11

Usage — consensus panel

from andamentum.llm_judge import judge_compare

result = await judge_compare(
    "The answer is 4.",
    "The answer is 5.",
    context="What is 2 + 2?",
    model=["anthropic:claude-haiku-4-5", "openai:gpt-5.4-nano"],  # a list -> panel
)
if result.needs_review:
    ...  # route for a second look — the panel disagreed or doubt was high

Loud failures, never silent defaults

Neither function ever swallows a model failure into a default answer. A failed tool-based call falls back to PromptedOutput exactly once (the pattern small and local models need); if that also fails, the exception propagates to the caller.

The mode lives in one parameter

There is one code path per function. The type of model is the only mode switch:

You passModeJudgesTemperature
model="ollama:gemma4:31b-nvfp4"Fastone0.0 (reproducible)
model=["m1", "m2", "m3"]Paneleach in turn0.7 (sampling)
model=["m", "m", "m"]Panelsame model, K draws0.7 (sampling)

A bare str is always the fast path; any Sequence[str] — even a one-element list — is always the panel path. A panel may be heterogeneous models or the same model repeated (mirroring the epistemic system's K-agreement idea); the panel mechanics don't care which.

Why the panel temperature is not zero

Fast calls run at temperature 0 for reproducibility. Panel calls run at a higher sampling temperature (PANEL_SAMPLING_TEMPERATURE = 0.7) for a load-bearing reason: at temperature 0, calling the same model K times returns K identical votes, so a same-model panel's agreement gate would be trivially unanimous and could never raise needs_review. Because temperature must be a first-class parameter, llm_judge constructs its own pydantic-ai Agent in elicit.py rather than routing through core.AgentRunner (which does not expose model_settings).

Schemas

Every boundary type is flat, or a list of flat models — at most one level of nesting — so small local models fill them reliably. Crucially, the model never fills these public types directly. It only ever fills a private, single-distribution elicitation schema (one criterion, or one comparison order); signals.py and panel.py assemble the public results from one or more of those calls.

Equal-weight roll-up limitation. Criterion has no weight field, so criteria are weighted equally. A confident fails on one important axis (say correctness) can be diluted by meets on several others. The mitigation lives in the prompt — judges are told to treat a confident factual or logical error as a serious fault within a criterion — not in the roll-up weighting. How confidence and doubt are derived

The two experiments both landed on the same core lesson: a verbalized distribution over discrete outcomes beats asking the model for a bare confidence number, and the reasoning must be written before the numbers (the derive-then-judge / G-Eval form-filling pattern). So the model is only ever asked to distribute 100 belief points; the two headline signals are computed from that distribution by pure, deterministic math in signals.py — no I/O, no LLM, unit-tested in isolation.

  • confidence = the mass on the reported verdict. Not the maximum mass — the mass on the label actually being returned. The two differ whenever a tie-break moves the verdict off the raw argmax: an even a/b split reports tie, and its confidence is the mass on tie, not the (larger) mass sitting on a and b. 1.0 means the distribution was one-hot.
  • doubt = normalized Shannon entropy. 0 = one-hot (maximally sure), 1 = uniform (maximally torn). It reads out how internally conflicted the judge was.

For judge_score, each criterion's three integers are normalized to a probability vector (by their actual sum, since small models drift off exactly 100 — a zero or negative total is a loud ValueError, never a papered-over uniform guess). The per-criterion vectors are combined by an equal-weight mean into one overall distribution; its argmax is overall, its max mass is confidence, its entropy is doubt. Ties resolve conservatively toward the more cautious verdict (fails > partial > meets).

The order-swap mechanism in judge_compare

Position bias is real and worst when the two candidates are close in quality. The literature's fix — bidirectional preference entropy (SCOPE, 2026) — is baked in: candidates are always labelled “Response 1” / “Response 2”, never A/B, so the elicitation schema carries no position information, and the caller controls which output is shown first.

Both orders always run, even in fast mode:

  • Order AB shows output_a as Response 1; order BA shows output_b as Response 1.
  • Each raw [p1, ptie, p2] is canonicalized back to [pa, ptie, pb] (BA just swaps the two ends).
  • The two canonical histograms are averaged; the winner is read off the order-averaged histogram — never a single order.
  • Any tie for the maximum mass (including an even a/b split) reports tie: a judge that split its belief evenly cannot honestly pick a winner.
  • If the winner flips between the two orders, order_consistent=False — a doubt signal in its own right that forces needs_review=True.

Panel consensus is an agreement gate

The single most important finding from both experiments: pooling judges does not boost accuracy over the best single judge. A panel's only validated value is as an agreement gate — a filter that tells you when to trust a verdict more and when to route it for a second look. So this module never fabricates a “smarter” averaged answer.

The panel runs strictly sequentially — one judge at a time, a plain for/await loop, never asyncio.gather — because Ollama serialises inference per process anyway, and the andamentum-wide rule is to never run two local-model calls concurrently. Aggregation mirrors epistemic.operations.integration K-agreement:

Panel signalRuleWhy
overall / winnerMajority vote across judgesBest-effort verdict, always returned. Deterministic tie-break — never insertion or dict order. A hung compare panel (judges split evenly between a and b) reports tie, never a: breaking toward a side would award the win to whichever output was passed first, reintroducing at the panel layer the position bias the both-orders machinery exists to cancel. A hung score panel lands on the more cautious label.
confidenceMIN across judges of each judge's mass on the reported verdictConservative: a panel is only as confident as its least-sure member. Never averaged up. Note what this is not — the minimum of each judge's confidence in its own verdict. On a split panel those differ, and only the former is meaningful: a dissenter's 0.80 belief in partial says nothing about the panel's confidence in meets.
doubtMAX across judgesA suspicion-raiser is never dampened by judges that happened to be more confident.
needs_reviewsplit, or doubt ≥ 0.5, (or order flip for compare)The one explicit trigger. A split panel always flags.

Locked semantics — never block the caller

On panel disagreement the functions return a best-effort majority verdict AND set needs_review=True. They never raise, never withhold, never return a null verdict. Disagreement is surfaced as a flag, not an error — the caller decides what to do with it.

The needs_review threshold is a single named constant, NEEDS_REVIEW_DOUBT_THRESHOLD = 0.5, one grep away from every predicate that uses it. The split trigger is structural and always reliable; the doubt trigger is a suspicion-raiser (see below).

How to read the signals

Read this before using doubt for anything

Doubt is a suspicion-raiser only. High doubt is a reason to escalate or route for a second look. Low doubt never proves the verdict is correct — it only means the judge was not internally conflicted. A stably-wrong model has low doubt. Any integration must use doubt to raise suspicion and trigger more scrutiny, never to grant trust or fast-track a decision.

The signal is reliable only for capable models. In the pointwise experiment, the error-detection band carried real signal for mini-class models (AUROC ≈ 0.74–0.77) but was essentially noise for nano-class models (≈ 0.57–0.59). Capability appears to gate it: a weak model tends to be wrong and confidently stable, so its distribution doesn't wobble when it's wrong. This module applies one uniform formula regardless of model tier (no tier branching), so weight doubt proportionally less when the judge is a very small model.

A panel is a filter, not an accuracy boost. Unanimity means trust the verdict more; a split means get a second opinion. Pooling does not produce a more accurate answer than the best single judge would have — its value is entirely in the agreement gate.

Put positively: use needs_review as the routing decision, confidence as a soft ranking key among comparable results, and treat order_consistent=False and a split panel as hard flags that the judgment is shaky. None of these signals is a substitute for ground truth.

Command line

The andamentum-llm-judge script exposes both functions as subcommands. --model is required (no hidden default); pass it once for the fast path, or repeat it / give a comma-separated list for a panel. Output is JSON to stdout by default (-o writes a file).

# fast single judge
andamentum-llm-judge score "Paris is the capital of France." \
    --context "What is the capital of France?" \
    --model anthropic:claude-haiku-4-5

# panel compare, custom criteria, write to a file
andamentum-llm-judge compare "answer one" "answer two" \
    --model ollama:gemma4:31b-nvfp4 --model ollama:gpt-oss:20b \
    --criteria my_criteria.json \
    -o result.json

A panel over the six default criteria is many strictly-sequential model calls (plus any PromptedOutput retries), so panel runs are noticeably slower than fast runs — accepted deliberately: correctness over speed, and there is nothing to parallelise against a serialising local backend. Exit codes: 0 success, 1 argument error, 2 input error, 3 judge call failed.

What the numbers say

Judge capability dominates everything. Same examples, same code: the capable judge goes 100% / 80%, the nano-class judge goes 80% / 50%. Nothing in the module compensates for a weak judge, and it does not try to — there is one uniform code path and no model-tier branching.

The doubt signal behaves as the experiments predicted. On the capable judge, doubt collapses to near-zero where it should (0.02 on compare, where it was right every time). On the nano judge it is scattered (0.61) — noise, exactly as the pointwise experiment found (error-detection AUROC ≈ 0.57–0.59 for nano-class vs ≈ 0.74–0.77 for mini-class). This is the empirical basis for the doubt caveat above, not a hypothetical.

Do not rely on needs_review to catch judge_score errors

On the capable-judge run, judge_score's gate flagged neither of its two errors. It flagged two examples, both of which were correct; both mistakes went through unflagged, confidently. The gate is a suspicion-raiser, and here it missed the suspicious cases.

At least one of those “errors” is arguably an artefact of the benchmark rather than the judge: SciFact's NOINFO gold maps to an expected partial, and the judge answered fails — a defensible reading of “the evidence does not support this claim”. The mapping is the debatable step, not the reasoning. Worth resolving before treating the 80% as a ceiling.

Practical guidance. judge_compare is validated and can be trusted as a preference signal on a capable judge. For judge_score as a learning signal, prefer a panel over a single fast judge: a panel adds the structural split-detection trigger, which does not depend on the doubt heuristic that failed here.

The compare gate, by contrast, did its job on the nano judge — 100% accurate on the 4 it left unflagged versus 67% on the 6 it flagged. That is the agreement gate working as designed: it cannot make a weak judge accurate, but it can tell you which of its answers to distrust.
