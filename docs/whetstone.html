andamentum sub-module

andamentum.whetstone

Structured review of drafts you wrote yourself, out to Word with tracked changes and comments.

CLI andamentum-whetstone · start at section 01 · sections 07 onward are internals

Point it at a draft you wrote and it hands back a Word file with a comment on every problem it found, a tracked change fixing what can be fixed by rewriting, and a check of every reference. Every finding is anchored to a verbatim quote from your document and dropped if that quote is not there — which is why a comment always sits on the words it is about.

Scope

Not a peer-review tool. Whetstone is for sharpening drafts you wrote. Do not run it on manuscripts, grants, or other documents shared with you in confidence as a reviewer, panel member, examiner, or editor. Most publishers and funders prohibit sharing such documents with AI tools, cloud LLMs included.

A confidentiality-marker tripwire refuses to run when it detects peer-review material, before any model call. --confirm-own-draft overrides it. See RESPONSIBLE_USE.md.

01Start here

One command does most of what whetstone can do. Everything else on this page is a way to change it.

# review your draft, get one Word file with comments, rewrites and a report
andamentum-whetstone draft.docx --model openai:gpt-5.4-mini \
    --out draft.reviewed.docx

That one run does five things:

  • Reviews the draft and writes each problem as a Word comment on the passage it concerns.
  • Rewrites what a rewrite can fix, as tracked changes you accept or reject.
  • Checks the references: every citation against the reference list, in any citation style, and each entry against Crossref (section 07). The editor answers these problems too.
  • Lists what the draft claims as new, so you can see what a reader will test you on.
  • Suggests a next step when problems remain: the exact command for the goal loop (section 06), which revises and checks again until they are gone.

Open the result in Word and work through it. Parts you do not want are switched off, not on:

FlagWhat it turns off
--no-editorThe rewrites. You get comments only.
--no-referencesThe reference check.
--no-lookupThe Crossref lookup only. The citations are still checked against the list, offline.

Two flags are required:

FlagWhat it changes
--modelRequired. Any pydantic-ai model id. There is no default — the tool will not guess what you meant to spend.
--outRepeat it. The format comes from the extension: .docx, .md, .html.

Two more you will want soon. --reviewer NAME picks who reads it — a claims reviewer and a methods reviewer notice different things, and section 02 lists the seven. --document-type tells it what kind of document this is, which it otherwise spends one model call working out.

What a run costs

A two-page draft is roughly thirty model calls and a minute of wall time on a hosted model. The draft goes only to the model you named. Two other things can leave your machine. The reference entries go to Crossref, which is on by default: they describe published works, and the text of the draft is never sent (--no-lookup stops it). The sentences that claim novelty go to a web search, which is off by default because those sentences are unpublished (--check-novelty turns it on).

02Choosing a reviewer

Who reads your draft changes what comes back. A claims reviewer checks whether your conclusions are supported; a methods reviewer asks whether anyone could repeat the work; a devil's advocate looks for the objection you have not answered. Pass one with --reviewer NAME.

andamentum-whetstone draft.docx --reviewer claims --model openai:gpt-5.4-mini \
    --out review.md

Leave it out and you get default: the criteria that suit the kind of document you gave it, which is what ran before reviewers had names. That is a reasonable first pass. The specialists are for when you know what you are worried about.

What you typeWhat runs
nothingThe ordinary review. Exactly as before reviewers existed.
--reviewer claimsOne specialist instead of the ordinary review — three criteria, not eight.
--reviewer default,claims,methodsThe ordinary review and two specialists, in that order, reconciled at the end.

A specialist replaces the ordinary review rather than adding to it — that is what makes it a specialist. Put default in the list to have both.

ProfileAsksNot suited to
defaultThe criteria that suit this kind of document. Used when you pass no reviewer.—
claimsDoes any conclusion outrun the evidence stated in the text?creative
methodsCould another group repeat this from the text alone, and is each choice motivated?external communication, essay, creative

Reviewers are orthogonal to document type, so each carries the set of types it suits and one predicate decides. A mismatch warns and proceeds rather than refusing: the classifier can be wrong, the user wrote the draft and asked for this reviewer, and the failure mode is a page of unhelpful findings rather than damage. The warning is written into the report header, not only into the terminal.

--criteria, --probes, --editor-criteria and --patch-author override a profile field by field, which is how the next profile gets written — start from one, change one thing. The run prints the effective configuration with the source of every value, so what actually ran is never a guess.

# list them, with a fit marker for a given kind of document
andamentum-whetstone reviewers --document-type academic

# one reviewer
andamentum-whetstone draft.docx --reviewer claims --model openai:gpt-5.4-nano \
    --out review.md

# start from a profile, change one field
andamentum-whetstone draft.docx --reviewer methods \
    --editor-criteria "precision,hedging" --model openai:gpt-5.4-nano --out review.md

Several reviewers at once

Give --reviewer a comma-separated list and they run in that order, each reading the same unchanged text. No reviewer in a list rewrites anything; they comment. Order matters in two small ways: findings are listed in the order the reviewers ran, and when two reviewers raise the same point at the same severity, the merged comment keeps the earlier reviewer's wording.

andamentum-whetstone draft.docx --reviewer claims,methods,adversary \
    --model openai:gpt-5.4-mini --out draft.reviewed.docx

Each reviewer signs its own comments, so Word's reviewing pane separates them without you naming anyone. A point more than one reviewer raised is one comment, not one per reviewer: it keeps the most severe reviewer's wording and names the others ("Also raised by: Claims reviewer"). There is one report, not one per reviewer.

The rewrites come from one editor pass at the end. It runs by default (--no-editor turns it off; naming editor in the list asks for the same pass). The line editor reads every reviewer's findings at once after the last one has finished and writes one set of tracked changes, signed by the line editor. Two findings on one sentence get one rewrite; two that pull in opposite directions are both declined and left to you; and where the reconciliation found the reviewers disagreeing, the editor is told not to settle it. The earlier design ran the editor inside every round, and five reviewers each rewriting the same abstract — each re-editing the last one's insertions — produced tracked changes with no paper underneath.

The novelty machinery runs once, in the first round. Later reviewers neither list the draft's claims again nor search for them — the claims do not change because another reviewer read the draft — so --check-novelty on a list costs the same as on a single review.

A run with more than one reviewer ends with a reconciliation — not a flag, because being handed four reports to cross-reference by hand is the problem it solves. It groups the findings that make the same point — each such group becomes the one merged comment above — and says where the reviewers disagreed, with both positions, because choosing between them is your call. The report opens with it, then one line per reviewer on how it read the draft, then every finding once. If the reconciliation fails, nothing is merged and the report says a point may appear more than once.

Cost

Each reviewer is a complete review. Three reviewers on a two-page draft took about three minutes and seventy model calls; one takes about a minute and thirty. The reconciliation adds one call on top, and the editor pass one call per section.

Checklist mode takes one reviewer, not a list. Its output is a coverage table whose rows come from one probe bank, and two banks in one run would give two tables that cannot be compared with each other or with the previous run — which is the property checklist exists for.

Under the surface a profile is a named bundle of the values the command line already accepts — criteria, probe ids, editor criteria, tracked-change author — plus a brief: a stance, the bar a finding must clear, and what the reviewer will not report. --reviewer claims and the equivalent flags typed out are the same mechanism, so anything a profile does stays doable by hand.

03Which mode do I want

Five things check a document, and they are not interchangeable. The first question is what you are asking for.

ModeThe question it answersOutputWhen
review default “Help me improve this draft” Connected findings plus synthesised prose Mid-draft, one document
checklist “Run the standard check” Fixed slots plus a deterministic coverage table Pre-submission, draft-vs-draft, CI
panel “What would reviewers say” N independent expert reviews plus a synthesis Before submitting, on your own work
andamentum-proofread (separate tool) “Is the prose clean” Readability scores and style flags Any time — no model needed
andamentum-references (separate tool) “Do my citations and my reference list agree” In a review: a comment on each problem citation or entry, and a summary. Alone: a list of problems Part of every review; alone, with no model — section 07

Review and checklist are complements, not rivals. Review notices what is not on any list and connects two distant problems into one root cause. Checklist cannot do either, and in exchange gives you output that is comparable between two drafts. Running both is a reasonable habit.

04Output

All three modes return the same ReviewResult, and all three renderers consume it unchanged.

render_markdown→ str
Findings grouped by priority, edits as diff blocks, author questions, document map.
render_html→ str
Self-contained page via typeset. The same structure, styled for reading.
render_docx→ PatchApplicationResult
Tracked changes for edits, Word comments for findings, and the review report prepended to the document.

Word output

Every finding is listed in the prepended report, and separately anchored as a comment where its quote can be located. The list is the record; the comment is the convenience. Three independent things stop a comment reaching a reader — a finding with no quote has nothing to attach to, an anchor can miss on text the converter reconstructed, and comments are invisible in viewers that do not render Word markup — so no finding depends on anchoring having worked.

What a report contains

Ordered by what a reader needs first. The AI-content banner and the provenance line, once — a warning that appears four times stops being read, so on a multi-reviewer run only the topmost report carries it. Then who reviewed and under what brief, because a methods reviewer finding nothing wrong with the argument is not a clean bill of health for the argument. Then the summary, the strengths and the weaknesses. Then the findings — must fix, should fix, consider, and within each group in the order they occur in the draft — each with the passage it concerns, what is wrong, one fix, and what the editor did about it: the suggested rewrite, or what is left to you. A finding and its answer are one item: in Word the comment says "Suggested rewrite: the tracked change here" or "Left to you: …", instead of a comment, a tracked change with no reason, and a separate list saying the same thing again. Then what the draft claims as new. Then the reference check — how the draft cites, how many citations were read, and what Crossref found — whose problems are among the findings above, signed by the reference checker. Last, when problems remain, the next step: the goal-loop command that would revise and check again, written to a new file so it does not overwrite this one. (In the Word report these two follow the summary.)

Last and quiet: one italic line naming the exact criteria, probes, editor criteria and author, each with where it came from, and the package version. It is provenance — worth having when you want to check what ran or compare two reports, and not worth the weight of a heading and a bulleted list at the top of the page.

Several reviewers give one report in the same shape: the reconciliation first, then each finding once, then your manuscript with every reviewer's comments and the editor's tracked changes in it. Reports still stack when you run whetstone again on a file it already reviewed — the earlier report is the earlier reviewer's record.

--document-type defaults to auto on the command line and in the Python functions alike, which spends one classifier call. Pass the type explicitly to skip the call. The editor is also on by default in both.

06The goal loop — review until it holds

Every mode above runs once. --goal instead sets a win condition and reviews, edits, and re-reviews the same draft until it holds — twice in a row, so the next round's ordinary edits cannot have quietly undone it — or the loop stops and says why.

# loop until a model judge agrees the flow is correct
andamentum-whetstone draft.docx --model openai:gpt-5.4-nano \
    --reviewer reader --goal "the flow is correct" \
    --out draft.reviewed.docx

What checks the goal is a separate question from what the review reads. --goal-check picks the check; --reviewer, --criteria and --document-type still pick what every round reviews against, exactly as in section 02.

--goal-checkWhat holds the goal
judged default A separate model call scores your goal text as one criterion, every round — never the pass that wrote the edit.
structure The active review criteria raise nothing major or moderate. Pair with --reviewer reader for "the flow is correct".
citations The reference checker of section 07 finds no problem: every citation points to an entry, and every entry is cited. Any citation style. Each round, its problems go to the editor next to the review's own findings, so the loop can fix a wrong citation number, not only report it. No Crossref lookup, because an edit cannot change what Crossref finds. Never whether a citation says what the sentence claims.
figures Each named figure's image matches its caption and the sentences that mention it. Needs --goal-figure and --figure-model below.

Flags

FlagWhat it does
--goal TEXTTurns the loop on. The win condition, in your own words.
--goal-check KINDOne of the four above. Default judged.
--max-rounds NHard cap on review-edit-review rounds. Default 4. Not the same flag as --rounds, which caps the gap loop inside one review pass.
--goal-figure LABEL=FILEOne figure to check, e.g. "Figure 1=fig1.png". Repeat for more than one. Required with --goal-check figures.
--figure-model MODELA multimodal model id, e.g. ollama:qwen3.8. Required with --goal-check figures.

--goal takes one reviewer, not a list, and it runs the editor every round, so --no-editor is refused with it — a round with nothing left to fix is what the loop is trying to confirm, not a step it should quietly skip.

How it stops

Never with an exception, and never by pretending. The run always finishes, writes real output, and reports a typed reason:

Stops withMeaning
goal_metThe check passed twice running. That round's own edits are discarded — a pass that already meets the goal gets no further unrequested rewrite.
no_progressA round with nothing to edit while the goal is still unmet, an edit with no net effect on the text, or the draft alternating between two earlier states.
cap_reached--max-rounds was reached with the goal still unmet.
unresolvableChecked once, before spending a round: for citations, no reference list and no citation notes, or no way to tell how the document cites; for figures, a named figure never mentioned in the text. Zero rounds run.

A run that stops without meeting the goal still writes a real, usable review. The CLI exits with code 1 instead of the usual 0, and one author question in the report names what it could not settle.

Figures need naming

Whetstone does not find figures in your document on its own. --goal-figure "Figure 1=fig1.png" names the label to look for and the image file to check it against — the label only needs the figure's number, so "Figure 1" also matches "Fig. 1" in the text. Locating and describing figures automatically is on the list, not yet built.

07Checking references

andamentum-references checks the citations of a draft against its reference list, and then looks up each entry in Crossref. It lists each problem with the text it concerns, what is wrong and what to do. Inside a review, the same check becomes a Word comment on the citation or entry.

# check the references; the lookup is on by default
andamentum-references draft.docx

# offline: citations against the list only, nothing sent anywhere
andamentum-references draft.md --no-lookup --json -o refs.json

# a model for what the text leaves open — a local one keeps it local
andamentum-references draft.pdf --model ollama:gemma4:26b

Every review runs it (section 01), before the review, so the editor answers its problems beside the review's own; each of its comments is signed by the reference checker. andamentum-references runs it alone, and needs no model. It exits 1 when it finds problems. It is also a goal for the loop in section 06 (--goal-check citations). In the loop it runs every round, without the Crossref lookup, because an edit cannot change what Crossref finds.

How it reads a draft

It first decides how the document cites, from evidence in the text: which candidates point to a real entry, and whether the list is numbered. Numbers that are not citations — exponents, units, affiliation marks, figure and table numbers — are set aside by rules before they count as evidence.

StyleLooks like
Numbers in brackets[3], [4, 5], [7–9] — IEEE, PLOS, BMJ
Numbers in parentheses(3) — Nucleic Acids Research
Superscript numbersdisease³ — Nature, Cell, AMA. Also read when a PDF or a copy-paste lost the formatting (disease3)
Author and year(Smith et al., 2020), Smith and Lee (2019) — APA, Harvard, Chicago author-date
Footnotes or endnotesChicago notes and bibliography, with or without a bibliography
Pandoc keys[@smith2020], against a list written [@smith2020] Smith, J. …

Inside a review, a Word file gives more evidence than its text: superscript formatting, Zotero, Mendeley and EndNote citation fields, and real footnotes and endnotes, and a PDF gives the same evidence, read from the PDF's own characters. andamentum-references reads a Word or PDF file as converted text, so it works from the text alone there.

A model only when the text leaves it open

Most documents are read by evidence alone and make no model call. A model is used only when you pass --model, and only for two questions: how the document cites, when the evidence is mixed, and whether an ambiguous number is a citation. Each call sees short excerpts, never the whole draft, and returns one flat answer, so a small local model can do it. Without a model these cases are reported as undecided, never guessed, and "never cited" is not reported while any candidate is undecided.

What leaves your machine

The lookup sends only the text of each reference entry to Crossref, never the text of the draft. --no-lookup sends nothing. "Not found" means that Crossref has no matching record; some conference papers and reports are not indexed there. When Crossref does not answer, the entry is reported as not checked, never as wrong.

How it is measured

A test set of 18 documents: the same references rendered in 13 real citation styles (CSL styles rendered by citeproc-py — APA, Harvard, Chicago author-date, Elsevier-Harvard, Springer, Nature, Cell, IEEE, AMA, NAR, PLOS, BMJ, MLA), three superscript styles again with the formatting removed, and two Chicago notes documents. Each has planted errors and distractors.

  • Word, with a model (ollama:gemma4:31b-cloud): 17 of 18 with every planted problem found and no false alarm. MLA cites by author and title with no year, and is reported as undecided.
  • Word, evidence only: no false alarm on any document. The texts that lost their formatting, and the notes documents, leave some candidates undecided.
  • PDF, with the same model: 16 with only the planted problems. The BMJ document also reports that its list starts at entry 3, which is true — the PDF converter dropped the first two entries.

Not checked: whether a cited work says what the sentence claims. Known limits: MLA (author and title, no year) is undecided, and a numbered list with only one entry is not recognised as numbered.

08The shared substrate

All three review graphs stand on the same deterministic ground, and only one step in it uses a model.

sectionizedeterministic
Heading-aware, size-banded split via the chunker's structural layer. Every section carries char offsets back into the source.
extract claimsone model call per section
The only extraction step. Claims come back as verbatim spans and are located in the source; anything that will not locate is discarded.
build document modeldeterministic
Section gists and a citation summary are computed, never generated. The summary — how the document cites, how often, and against how long a list — comes from the reference checker of section 07, with no model and no lookup, so a review and a reference check agree about whether a draft cites anything. Criteria that weigh evidence see it as one line. The result is the shared store every later stage queries.

Review stages do not receive the whole document. They get a sections table-of-contents with gists, the claims, and two tools — read_section and search_paper — and fetch what they need. That is what keeps the design document-type agnostic: nothing in the model knows which section is “Methods”, and a blog post has none.

09Review mode — the criterion cascade

One agent call per criterion, run in sequence, each seeing what the earlier ones found. That threading is the point: a later criterion can say the evaluation is weak for the same reason the introduction overclaims, which is a judgment about the document as a whole and the kind of finding that changes how an author revises.

Document type routes to one of six criterion sets, auto-detected by a one-shot classifier or set explicitly.

academic · external_communication · essay · tutorial · creative · general

Pipeline

sectionize → extract claims → build model → run criteria
  → verify findings → gap loop → consolidate
  → [novelty check] → gate → synthesise → critique & revise
  → [editor] → finalize
  • verify findings — locate every quote in the source; drop what cannot be anchored. The hallucination gate.
  • gap loop — bounded re-grounding pass for findings that came back thin.
  • consolidate — merge near-duplicates so the author reads one comment instead of nine.
  • novelty — three nodes, split across the disclosure boundary. Flag runs on every review and lists what the draft claims as new; search and judge stay behind --check-novelty and go out over deep_research, whose import is deferred until you ask for it. Finding the claims costs one call to the model that has already read every word of the draft, so it discloses nothing further. Verifying them sends those sentences to a search engine, which was never reading the document — so that half is off by default, and an unpublished manuscript reaches a third party only when you decide it should. The list is worth having without any search: seven claims came out of a two-page demo draft, several of them unsupported anywhere in its own text. It also puts the flag in front of you at the moment it means something, holding the exact sentences that would be sent. At most 8 claims are flagged, so a search costs at most 8 search fan-outs plus 8 judge calls. Nothing is rendered when the draft stakes no claim, which is the ordinary case for a tutorial or a short story. In a list of reviewers the whole check belongs to the first round: the draft's claims do not change because a second reviewer read it, so later rounds neither flag nor search, and the report carries one list.
  • editor — proposes concrete Edits, which become tracked changes rather than comments. On by default from the command line (--no-editor turns it off); editor=True in Python.

Criteria are data. Pass criteria=[Criterion(...)] to supply your own, or guidelines_text="…" to have a set of reviewer guidelines decomposed into criteria in one call.

10Checklist mode — the probe bank

The cascade asks evaluative questions: “are claimed results backed by evidence?” A small model answers “yes, broadly” and produces nothing. A probe asks for extraction under a quota: “find the 3 claims the reported results support least well.” That is a task a 20B local model does reliably, and it returns the same shape every run.

Presence

The defect is in the text

The probe returns a verbatim quote. Verification locates it, or the finding is dropped — the same gate review mode uses.

Absence

The defect is something missing

No quote exists, so the probe names the missing item plus the terms that would appear if it were present. If any term turns up, the finding is discarded.

The absence rule is deliberately conservative. A false “you never state your sample size”, sitting next to a paragraph stating it, is the most damaging thing this mode can emit, so a single hit refutes the claim rather than requiring all of them to.

A probe

idstr
Stable snake_case identifier. The join key for cross-linking, the coverage-table row, and the finding's category — renaming one is a breaking change to saved output.
instructionstr
One defect class, defined precisely enough that two readers would agree what counts. “Find 3 issues with the methods” is what this design rejects: issue is undefined, so the model invents its own bar and it moves between runs.
quotaint | None
3 means “find the 3 most serious” — a ranking with fixed output size. None means “report every instance; empty is a valid answer”. Use a quota only where the defect is near-universal; forcing one where the defect is often genuinely absent manufactures findings.
shapepresence | absence
Selects the output schema and the verification route.
tagstuple[str, ...]
Optional closed label set. Out-of-set answers are dropped rather than repaired, so the drop rate reads as what it is: whether the model can follow a closed set at all.

Fourteen probes ship as the default bank — a nine-id core, re-skinned academic versus general, plus per-type additions, so any one bank is nine to eleven probes. They are a default, not a schema: pass probes=[Probe(...)] for a house checklist.

What it deliberately does not reuse

Predictability is the product, so three stages from review mode are absent on purpose. A future reader should not “fix” the omission.

  • consolidate — a stochastic merger makes counts wobble between runs of an unchanged document, destroying the comparability the mode exists for.
  • the gap loop — how many rounds fire depends on what the first pass happened to return.
  • LLM synthesis — the summary is a computed coverage table, so two runs of a clean document produce the same table.

In place of consolidation, findings landing on the same passage are cross-linked and both kept. That records co-location, not agreement: the checks have different instructions, so the ordinary case is one passage carrying two different defects.

The coverage table

Rows come from the bank, not from the findings, so a probe that found nothing still has a row. Three states that look alike and mean entirely different things are kept apart:

CellMeaning
3 of 3Ran, found three, quota saturated — may be hiding more.
0Ran, found nothing. A result: the defect was looked for and is not there.
0 (3 unverifiable)Ran, found three, all failed the anchoring gate. Nothing was established.
not runThe probe crashed. Absence of checking, never rendered as absence of defects.

Conflating the last two with a bare 0 is the single failure this mode is built to avoid: it reports a clean bill of health for a check that established nothing.

11Panel mode

A different shape again — N expert biosketches are generated from the document's own subject matter, each writes an independent scored review, and a synthesis reconciles them. Its own graph, invoked by its own subcommand.

Panel requires --i-am-the-author. Simulating peer review of someone else's manuscript is exactly the use the tool refuses, so the gate is explicit rather than implied.

12Anchoring, and how it is measured

A review does not search for where a comment goes. The reviewer reads the text of the Word file that it annotates: a .docx is read as the text of its own paragraphs, and any other input is first written out as a Word file and read as that file. So each quote and each edit carries offsets into the file being written, and a comment is placed at those offsets. A document whose text does not match what was reviewed stops the render with an error, and nothing falls back to a search. The design that this replaced searched a converted rendering for each quote, and lost 15 of 43 rewrites on one real manuscript.

One path still searches: apply-patches, whose input is a list of text patterns with no offsets. There, matching is exact after normalisation, never fuzzy. A retry strips decoration the converter added, which is still an exact match of a smaller target and so cannot land on text that is not there. When a target occurs more than once the match is refused rather than guessed: a comment on the wrong sentence is worse than no comment, because the reader cannot tell it has moved.

A deterministic benchmark for that path — no model, no network — generates a corpus with a known answer key and scores three outcomes.

uv run python -m andamentum.whetstone.tests.anchor_bench
ConstructQuotesCorrectWrongMissed
plain, tabs, tables, lists, runs, headings, typography464600

Anchor rate alone is a bad target because guessing maximises it. wrong is the number that must stay zero, and a test fails if it does not. The two remaining misses are genuinely repeated sentences, correctly refused.

    print(finding.severity, finding.title, finding.quotes)

# references — any text; model only for what the text leaves open
from andamentum.references import check_references
report = await check_references(text, lookup=False)
for problem in report.problems:
    print(problem.headline, problem.start, problem.end)

Every function that calls a model takes model as a keyword-only argument. There is no shared config, no ambient default, and no silent fallback.

14Provenance

Output is marked as AI-generated in three places at once, and the markers are not decorative.

  • A visible banner on every rendered report, naming the model and date. --no-visible-watermark removes it.
  • Word core properties are stamped regardless of that flag, so the File → Info pane shows the provenance even on an unwatermarked render.
  • Tracked changes are attributed to andamentum-whetstone (AI). Overriding that name requires --allow-author-override and prints a warning: presenting AI edits as a human reviewer's may constitute research misconduct under most institutional codes.

andamentum-whetstone verify-provenance FILE reports what a document carries, without a model and without modifying it.
