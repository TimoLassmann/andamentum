## Project

Andamentum is a single Python package (`src/andamentum/`) of tightly-scoped sub-modules for building agentic reasoning pipelines. The core three were consolidated from separate packages; the commit history around that migration is relevant context.

- `andamentum.epistemic` — formal epistemology: evidence/claims/uncertainty entities, deterministic stage gates, pattern-driven work scheduling, multi-agent verification
- `andamentum.deep_research` — web research pipeline (search → fetch → extract → verify → synthesize) built on `pydantic-graph`
- `andamentum.document_store` — SQLite + FTS5 + sqlite-vec personal knowledge base with 4-signal Reciprocal Rank Fusion search and LLM metadata extraction. Retrieval is deliberately two-stage: `search` ranks **documents** by an RRF sum, and `get_chunks` / `get_chunk` expose the **passages** underneath with a stable id, so a caller can rerank them (`rerank` + `select_relevant`, behind the optional `rerank` extra) instead of thresholding an RRF score that has no absolute meaning
- `andamentum.whetstone` — structured criterion-cascade review over your own drafts. `await review_document(source, *, model)` is the default entry point: pydantic-graph driven, deterministic substrate (sectionize + claims digest) feeding a one-call-per-criterion review with a gap-loop re-grounding pass, optional editor, and synthesis + self-critique. Returns a `ReviewResult` with confidence-tagged `Finding`s, concrete `Edit`s (when `editor=True`), `AuthorQuestion`s, and a synthesised `summary`. Three renderers (`render_markdown`, `render_html`, `render_docx`) consume the same result; the docx renderer feeds an in-tree track-changes machinery (`whetstone.docx`) by handing each `Edit`/`Finding` its own offsets as a span — the reviewer read the annotated document's text, so no matching happens on the write side. A second review round over the first round's output is the same call with a different `author=` — nothing else. Document type routes to one of six pluggable criterion sets (academic / external_communication / essay / tutorial / creative / general) auto-detected via a one-shot classifier or set explicitly. **Reviewer profiles** (`whetstone/v3/reviewers.py`) are the named alternative to typing a criteria string: seven of them — `default` (named `default` rather than `general` because `general` is also a document type; it carries the document type's own criteria and probes, so a `default` run is byte-identical to a run before profiles existed), `claims`, `methods`, `framing`, `reader`, `adversary`, `editor`. A profile bundles values the CLI already accepts (criteria, probe ids, editor criteria, tracked-change author) plus a `brief` — a stance, a bar and an exclusion list rendered into the criterion, probe and editor prompts, and empty for `general` so those prompts render exactly as before. `--criteria` / `--probes` / `--editor-criteria` / `--patch-author` override a profile field by field; `resolve()` is the one place that precedence lives and it reports the source of every value, which the CLI prints. **`--reviewer` takes a comma-separated list** and runs them IN SEQUENCE over one unchanged text: no round edits. Each reviewer signs its own comments with the profile's identity, and nothing is written into the file between rounds: the rounds share one unchanged text, so every finding's offsets address the same document and one render writes the result. **The editor runs once, at the end** (`v3/editor.py:edit_findings`): with `--editor`, or with `editor` anywhere in the list (the two spellings are the same run; `editor` is pulled out of the rounds, since as a round it would run claim extraction, synthesis and self-critique to produce nothing), one editor pass reads every reviewer's findings, tagged by reviewer, plus the reconciliation's disagreements (rendered into its brief as passages NOT to settle), and writes one set of tracked changes signed by the line editor. Per-round editing was the previous design and it produced five reviewers' style passes over one abstract, each rewriting the last one's insertions — tracked changes with no paper underneath; and two findings on one sentence from two rounds could never meet in one call, so the prompt's own conflict handling (one rewrite for two findings, `can_fix=false` for two that pull in opposite directions) could not fire. Pooling is sound only because no round changes the text, so the CLI checks the projection is identical after each round and fails loud otherwise. A single reviewer keeps its in-graph editor, which already sees all of its findings. A list of more than one ends with `v3/reconcile.py` — one call that sees every finding by id (`R2.3`), groups the ones that make the same point, and reports where the reviewers disagreed (both positions kept; choosing is the author's judgement). `merge_agreed` then turns each group into ONE finding — the most severe member, `corroborated_by` naming the other reviewers — after checking the ids (unknown ids ignored, a group left with one reviewer merges nothing). One call decides both the summary's agreed list and the merge, so the two cannot disagree; a failed call merges nothing and the summary says duplicates may remain. Also not a flag. All three renderers get the same combined result (`combine_reviews`), each finding tagged by its reviewer via `perspective`; `render_docx(comment_authors=...)` signs each comment by its reviewer. A specialist REPLACES the document-type criteria rather than adding to them — put `default` in the list for both. Checklist mode refuses a list: two probe banks in one run give two coverage tables that cannot be compared, which is the property checklist exists for. Reviewers are orthogonal to document type, so each profile carries a `fits` set and one predicate `fits(*, profile, document_type)` decides compatibility — a miss warns and PROCEEDS (the classifier can be wrong and the user asked for this reviewer), and the warning is written into the report header rather than left in terminal scrollback. Criteria live in `v3/criteria.py` as module-level constants that both the type sets and the profiles reference, so each question has one wording; a test asserts identity (`is`, not `==`) so a copy-paste cannot create a second. Novelty is split across that boundary and the split is the point: the **flag** node runs on EVERY review and lists what the draft claims as new (`ReviewResult.novelty_claims`, rendered as a "Claims you are staking as novel" section in all three renderers, omitted when empty); the **search** and **judge** nodes stay behind `--check-novelty` / `check_novelty=True`. Finding the claims costs one call to the model that has already read the whole draft, so it discloses nothing further; verifying them sends those sentences to a search engine, which was never reading the document — not a step to inherit from a default on an unpublished manuscript. The listing is worth having on its own (seven claims came out of a two-page demo draft, several unsupported anywhere in its own text) and it puts `--check-novelty` in front of the reader holding the exact sentences that would be sent. At most `novelty_target_cap=8` claims are flagged and searched. In a reviewer list the whole check belongs to round 1: the CLI passes `flag_novelty=index == 0` (and gates `check_novelty` the same way), so later rounds spend no flag call and the report carries one list. Panel mode (multi-expert simulated peer review) lives in its own graph (`whetstone.v3.panel`) and is invoked via the `andamentum-whetstone panel` subcommand. Checklist mode is the third graph (`whetstone.v3.checklist`, `await run_checklist(markdown, *, model)` / `await checklist_document(source, *, model)`): instead of the criterion cascade it runs a fixed bank of `Probe`s — one defect class each, phrased as extraction under a quota ("find the 3 claims the evidence supports least well") — and summarises with a deterministic coverage table instead of synthesised prose. It deliberately does NOT reuse `consolidate`, the gap loop, or LLM synthesis: predictability is the product, so the cost is one agent call per probe (tool turns bounded by a per-probe usage limit) on top of the shared claim-extraction pass, the table's rows come from the bank rather than from the findings, and two runs over an unchanged document stay comparable row for row. Style / readability checks live in the separate `andamentum.proofread` module — the two are deliberately disjoint pipelines.
- `andamentum.scribe` — structured document drafting: block-based authoring (paragraph, heading, figure, table), section abstraction, built-in `article` scaffold (no grant scaffold — funder AI-disclosure rules are tightening and we don't want to make AI-assisted grant drafting more frictionless), SQLite-backed source of truth, one-way render to `.docx`. Replaces the standalone `document-tools:doc-draft` plugin.
- `andamentum.figures` — publication-quality scientific figure generation: 10 chart types (including `stacked`), 7 journal palettes and the `andamentum` report palette, a `report` preset that matches the design system (transparent background, design-token colours, Inter, text kept as text in SVG, `inline_svg` for dropping into a page), journal-matched sizing, auto chart-kind selection, and auto bar orientation (long-categorical-label bar charts auto-flip to horizontal — overridable with `horizontal=True/False`). `scribe_glue.insert_figure` renders + inserts into a scribe section in one call. Absorbed from the standalone `mosaic-figures` package.
- `andamentum.chunker` — structural-first semantic chunking of long markdown into 2k–10k char self-contained units. Stage 1: split at markdown headings. Stage 2: embedding-based split for over-budget sections. Stage 3 (optional): small-LLM judge for grey-zone boundaries. The LLM is never the primary segmenter.
- `andamentum.harvest` — universal source → markdown extraction. Single async API: `extract(source: str | Path, *, mode="fast") -> str`. Detects format (PDF / HTML / DOCX / PPTX / Markdown / plain) and dispatches to the best backend; for HTML, sniffs `og:type` / JSON-LD `@type` and routes article-like pages to trafilatura, index/listing pages to Docling, and races both extractors when the page metadata is ambiguous (picks the higher-scoring output by structural quality). Two Docling configurations behind one `mode` parameter: `"fast"` (default, standard threaded pipeline, no OCR) and `"accurate"` (VLM pipeline + per-figure descriptions, PDF only, needs the `vlm` extra).
- `andamentum.vision_critique` — bounded vision critique of rendered figures. Single async API: `await critique_figure(image, *, model) -> FigureCritique`. Image is bytes / Path / http(s) URL; model is any pydantic-ai multimodal id (Ollama, Anthropic, OpenAI). Schema is a tight pydantic model with close-set enums (`label_overlap`, `labels_legible`, `legend_blocks_data`, `aspect_ratio_issue`, `suggested_fixes` from a fixed `Literal` set, `confidence`, `one_line_summary`) so small local vision models can fill it reliably, plus `has_issues` — a computed field the model never fills, derived from the other seven and present in the serialised JSON but deliberately absent from the validation schema (a `@computed_field` enters the serialization schema only, so pydantic-ai keeps asking for seven fields; `tests/test_api.py` pins both halves). Calibration is a **list, not a single model**: `CALIBRATION_MODELS` in `tests/test_api.py` names every model certified against the committed `broken_bar.png` fixture, the `@pytest.mark.ollama` test is parametrised over it, and a model the local Ollama does not serve **skips rather than fails** — the list records what is certified, one machine holds a subset. Certified: `ollama:qwen3.8:27b-mlx` (measured 2026-09-06 — `label_overlap=True`, `labels_legible=False`, confidence 0.98, 23.5 s cold; already pulled for `harvest` accurate mode, so the module adds no new download). `gemma4:e4b-it-q4_K_M` was the previous certified model and is retired — it is no longer in use and no longer pulled here. `gemma4:e2b` never qualified: it fails the fixture, confidently reporting the figure is fine. Add a model to the list before recommending it anywhere. Used standalone, by `figures` for figure refinement, or by other modules that want to lint rendered output.
- `andamentum.proofread` — deterministic, dependency-light proofreading. Single sync API: `analyze(text: str) -> ProofreadResult`. Combines five readability scores (SMOG, Flesch–Kincaid grade, Flesch reading ease, Gunning Fog, Coleman–Liau, ARI) with classic style checks (weasel words à la Matt Might, passive voice via be-verb + past-participle heuristic, duplicate words, weak sentence openers, -ly adverb density). No LLM, no I/O, pure function. Designed to complement `whetstone`'s LLM-driven review, not replace it. Findings carry char offsets and `sentence_index` so callers can map back into the source. The CLI (`andamentum-proofread`) accepts URLs and document files via `harvest.extract` — the only point where the module touches another sub-module.
- `andamentum.typeset` — standalone typesetting system (7 visual atoms, 3 named styles, HTML + PDF output) used by other modules for rendering
- `andamentum.agentic_dialect` — the house style for building agentic graph systems (pydantic-graph + pydantic-ai), as data + portable conformance checks. The prose canon is `src/andamentum/agentic_dialect/DIALECT.md` (3 surfaces / 2 roles / 1 agent / 9 laws); the structured laws, role briefs (`for_role`), checklist, and skeleton are the enforceable kernel, drift-tested against the doc. `check_code(path)` runs the portable static gates (no engine import in workers, no `dict[str, Any]`, no nondeterminism/client/literal-bound in node bodies). A leaf module: depends only on `pydantic` + stdlib, imports no other sub-module, relative imports only — kept independently extractable.
- `andamentum.forge` — the meta-system: a natural-language brief → a runnable agentic system, built **in** the dialect and held **to** it (the pair to `agentic_dialect`, which defines/verifies the style). `await run_forge(brief, *, model, dest=None, ...)` is the entry point: one `pydantic-graph` pipeline — understand → frame → decompose → compile → review → render → verify → build → audit. The model *declares* each node's kind and `consumes`/`produces` freely; then deterministic code does the heavy lifting — `assemble` matches producers→consumers into a DAG (fan-in/out/loops fall out; nothing forced linear), `diagnose` (rapidfuzz) gathers every structural flaw with a concrete fix, and a bounded repair loop re-types flagged nodes or **fails loud**. `compile_spec` validates against the recipe (the `SystemSpec`); `review` is the **plan manager** — a deterministic per-area coverage check (`plan_coverage`, blocking `UNCOVERED_AREA`) plus one goal-vs-plan LLM call (`review_plan`) that on reject loops back to `Frame` carrying its concerns, bounded by `MAX_PLAN_REVIEW_ROUNDS` (fail-loud at the cap); `render` deterministically assembles the package (Assembly law — no LLM writes final code), leaving `NotImplementedError` holes; `build` has agents author the bodies behind a static gate suite (contract + read/write coverage + purity + no-swallow — suggestions turned into verified guarantees) plus an advisory **component manager** (job-vs-body) that feeds objections into the repair loop but never downgrades a gate-valid body (kept, with any residual objection recorded as a `BuildConcern`); `audit` runs the built system's tests + smoke + `check_code` + a critic in a sandbox. LLM-written code executes **only** in the sandbox (`sandbox.py`, **Podman by default** — host-isolated; subprocess fallback; `Containerfile` ships the image). Reuses the deterministic core from the exploratory `scratch/forge` dump; the design/build loops are the dialect-clean rewrite.
- `andamentum.llm_judge` — LLM-as-judge primitive. Two async entry points: `await judge_score(output, *, criteria=None, context=None, model=...)` (score ONE output per-criterion) and `await judge_compare(output_a, output_b, *, ...)` (which of TWO is better). No graph — one call, or a sequential fan-out with a deterministic roll-up. **Mode lives in the `model` parameter's type**: a `str` → FAST path (one judge, temperature 0, reproducible); a `Sequence[str]` → PANEL path (one call per model, strictly sequential, sampling temperature 0.7 so a same-model-repeated panel actually varies). Every verdict is a *verbalized distribution* (reasoning first, then belief points over three outcomes), from which `confidence` (max mass) and `doubt` (normalized Shannon entropy) are DERIVED — never asked of the model. `judge_compare` always runs BOTH presentation orders and averages, because a single-order call has position bias. Panel pooling is **an agreement gate, not an accuracy boost**: the verdict is the majority vote, `confidence`/`doubt` aggregate conservatively (min / max), and a split panel or an order flip sets `needs_review=True` — a routing hint that never blocks the caller. `doubt` is a **suspicion-raiser only**: high doubt warrants escalation; low doubt never proves the verdict correct (and the signal is noise on nano-class models). Criteria default to six domain-agnostic axes; callers pass their own for a domain.
- `andamentum.core` — shared model-resolution, `AgentRunner`, and embedding infrastructure (`core.embeddings`) used by all sub-modules

Everything ships in one distribution. The default dependencies are the flat union of what the sub-modules need. Three optional extras add heavier, self-contained capabilities with graceful fallback when absent: `html-articles` (trafilatura, Apache-2.0 — falls back to docling), `pdf` (WeasyPrint, BSD-3 — `typeset` raises a clear ImportError without it), and `rerank` (sentence-transformers, Apache-2.0 — `document_store.rerank` raises an ImportError naming the extra; nothing in the store calls it, so an install without it behaves identically). A fourth, `vlm`, is documented under harvest.

## Commands

Use `uv run` for everything Python-related — `uv run python`, never plain `python` or `python3`, including one-off `-c` snippets and throwaway checks.

**Never write scratch artefacts into the repo.** Screenshots, rendered previews, sample outputs, temp scripts, benchmark dumps and anything else generated while working goes in the session scratchpad directory, not in the working tree. That includes tool output directories such as `.playwright-mcp/` — pass an absolute scratchpad path when a tool asks where to save. The only files that should appear in `git status` after a task are the ones the task was actually asked to produce.

```bash
# Install dev deps
uv sync --extra dev

# Run the full test suite (asyncio_mode=auto; see the canonical green state below)
# The `ollama`, `benchmark`, `cloud`, and `live_provider` markers are deselected by default.
uv run pytest

# Run the 200-query semantic routing benchmark (requires live Ollama)
uv run pytest -m benchmark -s

# Run tests for a single sub-module
uv run pytest src/andamentum/epistemic/tests
uv run pytest src/andamentum/deep_research/tests
uv run pytest src/andamentum/document_store/tests

# Run a single test file / test
uv run pytest src/andamentum/epistemic/tests/test_gates.py
uv run pytest src/andamentum/epistemic/tests/test_gates.py::test_name -x

# Type check (pyright, targets Python 3.13 per pyproject.toml)
uv run pyright

# Lint
uv run ruff check
uv run ruff format

# Build distribution
uv build
```

The canonical green state: **pyright 32 errors (test-only typing noise — pydantic-graph generic variance in `test_topology.py` and in the `_Ctx` stand-in that several `v3` node tests pass to `run()`, `Decomposition` dict-form fixtures in several test files; zero errors in shipped `src/` code. ### Patch-only mode for `andamentum-whetstone`

The patch-only path is the analogue of a standalone "apply review patches to a Word file" script: feed it a .docx and a JSON array of `DocumentPatch` objects (the type defined in `whetstone/models.py`) and it produces a tracked-changes .docx. It is the only remaining caller of `whetstone.docx.finalization.finalize_reviewed_document` and of the text-pattern matcher in `patch_editor.py` — the review pipeline goes through `finalize_annotated_document` instead, because it already knows its coordinates.

```bash
andamentum-whetstone draft.docx \
    --apply-patches patches.json \
    --out draft.reviewed.docx \
    --patch-author "Claude" \
    --patch-report review-summary.md   # optional markdown to prepend
```

`patches.json` is a JSON array; each element is a `DocumentPatch` with `patch_type` ∈ {`text_edit`, `comment`, `document_analysis`}. `text_edit` requires `text_pattern` + `new_text` + `explanation`; `comment` requires `text_pattern` + `comment_text` + `explanation`. This is the foundation for AI-driven draft → review → revise loops where Claude (or another agent) drafts patches separately and then applies them in one tracked-changes pass.

## Architectural conventions

**Explicit model argument, no hidden defaults.** Every public function that calls an LLM takes `model=` as a keyword-only argument. There is no shared config module, no silent fallback, no ambient default. When adding new LLM-calling code, match this pattern — don't reach for a global config.

**Confusable parameters are keyword-only.** Any parameter that is one of two or more same-typed, semantically confusable values — model names, identifiers, paths, source/target pairs — goes behind `*`. This applies to **private helpers**, not just the public API. The reason is that transposing two `str` parameters is invisible to pyright: the values simply swap and the failure surfaces far from the call site. Behind a `*` the same mistake is a `reportCallIssue` error at every call site, checked without needing a test to exercise that path.

This is not a blanket rule — genuinely positional signatures (`cosine_similarity(a, b)`, `_pct(numerator, denominator)`) stay as they are. It applies where the confusable values are *passed onward* rather than consumed locally, so a swap produces wrong behaviour instead of an immediate error. Retrofit opportunistically when touching a file; don't sweep the repo.

Worked example — `document_store/public.py:_preflight` took `(database, embedding_model, model=None, *, auto_repair=True)`. A caller passing `(database, model, embedding_model)` handed the embedding service an LLM id, breaking every `search()` call, and neither pyright nor the test suite could see it. The `*` now sits directly after `database`.

**Core module** (`andamentum.core`) — shared infrastructure for model resolution, agent execution, embeddings (`core.embeddings`), and SSRF-safe URL fetching (`core.url_safety`). All sub-modules import from core instead of maintaining independent implementations. When adding LLM-calling code, use `core.agents.AgentRunner` or `core.agents.run_agent_with_fallback()` — they provide model resolution (ollama, bedrock, passthrough) and PromptedOutput fallback for free.

**Layering:**
- `core` is the shared base — no sub-module imports from another sub-module via core's surface (core itself depends on neither).
- `document_store` is foundational; `epistemic` may depend on it directly (e.g., `EpistemicRepository` wraps a `DocumentStore`).
- `deep_research` is foundational for evidence gathering; `epistemic.evidence_gathering` may depend on it.
- `document_store` and `deep_research` MUST NOT depend on `epistemic` or on each other.
- `whetstone` depends on `core` (for `AgentRunner`/`AgentDefinition`, and for `core.models.resolve_model`, which the checklist probe runner calls directly because it constructs its own pydantic-ai `Agent`), on `typeset` for HTML rendering, on `chunker` for section splitting, on `harvest` for source ingestion, on `deep_research` (only when the opt-in novelty check is enabled — `--check-novelty` / `check_novelty=True`; otherwise the import is deferred at runtime), on `vision_critique` (only for the goal loop's `--goal-check figures`) and on `llm_judge` (only for the goal loop's `--goal-check judged` — a separate `judge_score` call every round, never the reviewer/editor pass that produced the edit). It MUST NOT depend on `epistemic` or `document_store`.
- `scribe` depends only on `typeset` (for HTML/PDF rendering) and stdlib `sqlite3`. MUST NOT depend on `epistemic`, `deep_research`, `document_store`, `whetstone`, `figures`, or `core`.
- `figures` depends only on matplotlib + numpy + pydantic. The optional `figures.scribe_glue` submodule is the ONLY place where `scribe` is imported; the rest of `figures` MUST NOT touch `scribe`. `figures` MUST NOT depend on `epistemic`, `deep_research`, `document_store`, `whetstone`, `typeset`, or `core`.
- `chunker` depends only on `core` (for `AgentRunner`, model resolution) and `rapidfuzz` (for tiered anchor matching). MUST NOT depend on `epistemic`, `deep_research`, `document_store`, `whetstone`, `scribe`, `figures`, or `typeset`. Other modules MAY depend on `chunker` (e.g. whetstone for section-by-section review on huge documents, document_store for embedding-quality chunks).
- `harvest` depends only on `httpx`, `trafilatura`, `docling`, `pypdfium2` (declared, not inherited: `pdf_probe` imports it directly so the text-layer probe costs no docling/torch import), and stdlib. The optional `vlm` extra adds `docling[vlm]` + `transformers` + `mlx-vlm`. MUST NOT depend on any other andamentum sub-module — it's a leaf service. Other modules MAY depend on `harvest` to convert URLs/files to markdown before further processing (e.g. chunker, whetstone, future deep_research consolidation).
- `vision_critique` depends on `core` (for `resolve_model`) and `pydantic` / `pydantic-ai` / `httpx`. MUST NOT depend on `epistemic`, `deep_research`, `document_store`, `whetstone`, `scribe`, `figures`, `typeset`, `chunker`, or `harvest`. Other modules MAY depend on `vision_critique` (e.g. `figures` for refinement loops, `whetstone` for figure review during manuscript checking).
- `proofread` library depends only on `pydantic` and `textstat`. The optional `proofread.cli` submodule is the ONLY place where `harvest` is imported — so the CLI can accept PDF / HTML / DOCX / PPTX / Markdown sources — and the rest of `proofread` MUST NOT touch `harvest` or any other andamentum sub-module. Other modules MAY depend on `proofread` (e.g. `whetstone` to attach deterministic readability scores to a review, `scribe` for pre-render style flags).
- `agentic_dialect` depends only on `pydantic` + stdlib. MUST NOT import any other andamentum sub-module, and uses only relative imports internally, so it stays independently extractable (a later spin-out to a standalone package is a `git filter-repo`). Other modules MAY depend on `agentic_dialect`. It is governance/knowledge, not a runtime pipeline — nothing in the data pipelines imports it.
- `llm_judge` depends only on `core` (for `resolve_model`), `pydantic` + `pydantic-ai`. It owns its own pydantic-ai `Agent` construction rather than routing through `core.AgentRunner`, because it needs `model_settings` (temperature) as a first-class parameter — the fast/panel temperature split is load-bearing, not cosmetic. MUST NOT depend on `epistemic`, `deep_research`, `document_store`, `whetstone`, `scribe`, `figures`, `typeset`, `chunker`, `harvest`, `vision_critique`, or `proofread`, and MUST NOT import `pydantic-graph` (there is nothing to route between — see the module docstring). Other modules MAY depend on `llm_judge` to score or rank outputs. A dialect-conformance test (`tests/test_dialect_conformance.py`) enforces the forbidden-import list and runs `agentic_dialect.check_code` in strict mode.
- **`epistemic` MAY depend on `llm_judge`** — one-way; `llm_judge` must never import `epistemic`, enforced by its own conformance test. The dependency is confined to the operation/graph layer, across **three** driver modules — each a bounded FAST-path second opinion (one `Criterion`, bare-`str` model, temperature 0, strictly sequential), never a replacement for the cheap primary judgment, and never able to change a verdict on its own: `epistemic/quality_doubt.py` (**two** TMS destroy gates, one module: `confirm_low_quality` gates invalidation of near-zero-quality evidence, called from `operations/evidence.py`, and `confirm_corruption` gates the `evidence_corrupted` sentinel, called from `operations/scrutiny.py` — a declined destroy at that second gate records a non-blocking caveat uncertainty and leaves the source's weight untouched), `epistemic/direction_opinion.py` (SITE A — confirms the direction of load-bearing evidence whose judgment was one-hot, so entropy carries no signal; bounded per pass and per claim) and `epistemic/scrutiny_opinion.py` (SITE B — a second reading when the deterministic scrutiny weight is borderline; both called from `operations/scrutiny.py`). The three share one record type, `entities/judge_opinion.py`. **Why three and not one:** `thresholds.py` records that small models emit one-hot judgments 53–82% of the time, so a doubt signal derived only from the primary judgment's own distribution is near-zero on most of the corpus — a second, independent elicitation is the only thing that makes the doubt escalation gate fire at all. `epistemic.judgment_signal` and `epistemic.thresholds` deliberately stay **import-free** of it: importing `llm_judge.signals` executes the package `__init__` → `panel` → `elicit` → `pydantic-ai`, and `judgment_signal` is imported by `entities/evidence.py`, a pure-stdlib leaf. The two modules hold one definition of doubt (`normalized_entropy` / `max_mass` / `normalize_three`, and the identical doubt cutoff) implemented twice and pinned equal by a drift test — `epistemic/tests/test_doubt_scale_single_source.py`, which also fails if a leaf grows an `llm_judge` import.
- `forge` depends on `core` (`AgentRunner` / `resolve_model`), `agentic_dialect` (laws for grounding the authoring heads + `check_code` for verifying output), `pydantic-graph` + `pydantic-ai`, and `rapidfuzz` (diagnostic near-miss matching); the sandbox uses only stdlib (subprocess) or the `podman` binary. MUST NOT depend on `epistemic`, `deep_research`, `document_store`, `whetstone`, `scribe`, `figures`, `typeset`, `chunker`, `harvest`, or `vision_critique`. `forge.runtime` is engine-free (`run_head` wraps `core`, `loop_allowed` is pure) so a **generated** package — which imports `andamentum.core`, `andamentum.forge.runtime`, `pydantic-graph`, `pydantic-ai` — stays itself dialect-conforming. `graph.py` is the only engine-aware file in the module.

**Public API lives in `__init__.py`.** Each sub-module's `__init__.py` defines `__all__` explicitly; everything not listed is internal. `document_store` additionally re-exports from `public.py` — that module is the authoritative public surface for document_store (14 functions: `ingest`, `search`, `get_chunks`, `get_chunk`, `find_by_metadata`, `describe_metadata`, `update_metadata`, `delete`, `restore`, `purge`, `list_deleted`, `repair`, `reembed_document`, `find_duplicates`). The read side is three uniform functions usable by humans and agents alike: `search` (unstructured content recall), `find_by_metadata` (structured query — scalar value = equality, list value = set-membership `IN`, plus `include_content=False` for cheap metadata-only overviews), and `describe_metadata` (schema discovery over the schema-less metadata — returns per-field `FieldProfile` with value distributions, bounded by `max_values`). The store stays domain-agnostic: consumers define their own metadata vocabulary and build their own tools on these primitives rather than the store growing a function per consumer.

**Evidence providers** follow a strict specification documented in `src/andamentum/epistemic/providers/CONTRIBUTING.md`. Read it before adding or modifying any provider. Key rules: providers retrieve and structure evidence, never assess quality (`quality_score=None` always), never truncate content, and return `list[GatheredEvidence]` (empty list on error, never raise).

**Epistemic architecture principles** (enforced across the module):
- **P1: Operations are pure transforms.** An operation reads entities, does work (LLM calls, computations), and writes the result back. It NEVER manipulates fields on other entities to signal what should happen next.
- **P2: The graph is the sole flow controller.** Only graph nodes (in `graph/nodes.py`) decide what runs next, based on operation results, entity state, and graph state.
- **P3: Entity fields are data, not signals.** Every field on Claim, Evidence, Objective represents something real — a verdict, a score, a stage. No field exists solely to tell the scheduler what to do.
- **P4: Graph state tracks pipeline progress.** `EpistemicGraphState` (in `graph/state.py`) tracks what work has been done and what needs doing — not entity fields.
- **P5: Operations don't reach across entity boundaries.** An operation on an Uncertainty does not modify Claims. Cross-entity effects are the graph's job.
- **P6: Every node has an explicit contract; routing decisions are data, not implicit imperative flow.** Each `Node` subclass (in `graph/base.py`) declares `reads` (state fields read), `writes` (state fields mutated), `operations` (operation classes dispatched via `_run_op`), and `post_invariants` (predicates that must hold after the node runs). Successors live in the `run()` return type annotation — pyright + pydantic-graph enforce them, and `graph/topology.py:topology()` exposes them as a Python value you can inspect, diff, and assert reachability over (see `tests/test_topology.py`). The recurring "silent dead zone" routing-bug class (where a node returns to a successor that doesn't continue work the claim still needs) becomes structurally detectable rather than benchmark-detectable. Cross-cutting data carried on entities (e.g. `Objective.decomposition` → `entities/decomposition.py:Decomposition`) uses typed Pydantic models, not `dict[str, Any]`, so consumers access fields by attribute and divergent-lookup bugs become impossible.
- **P7: Lazy escalation — each layer asks for what it's missing; breadth comes from demand, not eagerness.** Planning, investigation, scrutiny, and synthesis don't pre-commit to a wide search. Each layer that detects insufficient evidence emits a `Demand` (`andamentum.epistemic.demand.Demand` — a 3-field flat `needs_more` / `justification` / `target_hint` Pydantic model designed for small Ollama models), and the graph routes that demand to the layer that can satisfy it minimally. Evidence gathering (both initial and follow-up rounds) flows through description-driven dispatch (`epistemic_dispatch_provider`): each provider class self-describes via `description`, `query_guidance`, `query_examples`, `output_kind`, and the dispatch agent is invoked once per provider in parallel — it either commits one or two native-syntax queries or abstains. Cross-domain convergence still requires ≥2 independent sources (Reichenbach common-cause), but the system reaches that threshold through per-provider commit/abstain rather than a separate tournament. Investigation rounds add a methodological *angle* on top of the claim: `epistemic_investigate_claim` generates intents (e.g., "adversarial replication"), and the dispatch agent receives the original claim as the subject plus the intent as the angle modifier — queries stay grounded in the claim's lexicon while exploring the intent's dimension. At synthesis, `CheckSynthesisDemand` runs cheap deterministic gates (open-research, no-combined-verdict, stranded-claims, decisive posterior ≥`POSTERIOR_DECISIVE_THRESHOLD` / ≤`1−POSTERIOR_DECISIVE_THRESHOLD`) before the LLM judgment, and on `needs_more=True` loops back to `Scrutinize` for the eligible claims. The load-bearing termination guarantee is the per-sub-claim cap (`PEIRCE_CYCLE_CAP`), not a global give-up budget. Add new "do more work" decisions to this scheme — emit a `Demand` and let the graph route it — rather than reaching for an eager broad-search shortcut.

**Epistemic core abstractions** (understand these before touching `epistemic/`):
- `entities/` — `Objective`, `Evidence`, `Claim`, `Uncertainty`, `Decision`, `Snapshot`, `Artefact` (all `EpistemicEntity` subclasses), plus `decomposition.py` (typed `Decomposition` / `SubInvestigation` for `Objective.decomposition`) and `cap_evaluation.py` (typed `CapEvaluation` for `Claim.cap_evaluation`, the cycle-cap provenance snapshot). `Objective.claim_to_verify` enables seed-claim verification mode (a Pydantic `model_validator` refuses Objectives that set both `claim_to_verify` and `decomposition` — they're mutually exclusive seed modes; `CreateClaims` would silently pick single-seed and discard the decomposition).
- **The verdict object** (`entities/verdict.py`). A run's decision is ONE typed `EpistemicVerdict` — posterior report, per-claim `ClaimVerdict`s with their `EvidenceRef`s, and a `VerdictProvenance` count block. It is built inside the graph by `CombineClaimVerdicts` (via `confidence.build_verdict`, which is its sole constructor), held on `EpistemicGraphState.verdict`, persisted on the frozen `Snapshot.verdict`, and returned as `PipelineResult.verdict`. Everything downstream — the synthesis prose's `> **Verdict:**` line, the CLI, the offline report, the HTML audit report — **renders** it and never re-decides. `entities.verdict.verdict_label` is the only place in the package that compares a posterior against `POSTERIOR_DIRECTIONAL_BREAKPOINT` (a source scan in `tests/test_verdict_single_source.py` pins that), and `display_label` maps the resulting *direction* onto the closed display vocabulary without a second comparison. When adding a consumer that needs "what did this run conclude", read the object — do not derive a label from a number or parse it out of prose. The predecessor fields `Decomposition.combined_verdict`, `CombinedVerdictData`, `Snapshot.combined_verdict` and `WriteAnswerOutput.verdict` were deleted, not deprecated.
- **Snapshot/Artefact indirection.** The final report is reachable from `Objective` via two routes — direct (`Objective.artefact_id → Artefact.content`, the 1-hop signal stamped by `SynthesizeReportOperation`/`SynthesizeInsufficientReportOperation` on completion) and via the immutable freeze (`Objective.snapshot_id → Snapshot.artefact_id → Artefact.content`, the auditable history). Both point at the same `Artefact`. `Objective` does NOT have a `report` attribute; readers looking for "where's the output" should use `Objective.artefact_id` for the load-bearing presence check (e.g. the synthesis stage exit invariant in `graph/stages.py:_check_synthesis`) and traverse the snapshot path when they need the immutable freeze that produced it. Artefacts have `artefact_type` ∈ {`summary`, `insufficient`, ...} — the typed signal that distinguishes a directional verdict from a fallibilism terminal (`SynthesizeInsufficient`); consumers check this field rather than parsing the verdict prose. The run's *decision* travels the same two routes: 1-hop live via `PipelineResult.verdict`, auditable freeze via `Objective.snapshot_id → Snapshot.verdict` (an `EpistemicVerdict`). The offline report reads the frozen one; it never recomputes.
- `gates.py` — `STAGE_GATES` + `validate_promotion`: deterministic, routing-aware checks that must pass before a `Claim` advances stages. Gates query the question type's routing profile and only require tracks that are PRIMARY or SECONDARY — not SKIP.
- `graph/` — pydantic-graph DAG scheduler. 23 nodes with typed return edges and explicit contract metadata (P6). Entry point: `run_epistemic_graph()` in `graph/__init__.py`. Key files: `base.py` (the `Node` class with `reads` / `writes` / `operations` / `post_invariants` ClassVars), `topology.py` (`topology()` reflection helper exposing the graph as a Python dict), `invariants.py` (reusable post-condition predicates like `no_stranded_claims`), `nodes.py` (the 23 concrete node classes).
- `operations/` — pure `BaseOperation` subclasses. Each takes an `OperationInput`, does work, returns `OperationResult`. They do NOT control flow — the graph does.
- `repository.py` — `EpistemicRepository` wraps a `DocumentStore` (from `andamentum.document_store`) — the persistence layer for all epistemic entities.
- `runner.py` — `DefaultAgentRunner` wraps `core.AgentRunner` with epistemic agent registry lookup.

**Deep research pipeline** is a `pydantic-graph` state machine. `state.py` holds `ResearchState`; `graph.py` / `nodes.py` define the nodes; `orchestrator.py` / `runner.py` drive execution. `searxng.py` manages the local SearxNG instance and `circuit_breaker.py` wraps it. Content extraction (`content_extractor.py`) uses `trafilatura` for HTML and `docling` for PDF. Search-query production runs through a per-slot generate→verify loop (`PrepareSearchCycle` → `GenerateOne` ⇄ `Verify` → `ParallelSearch`): the `query_generator` agent emits one query at a time, the `topic_verifier` agent judges it against the goal, rejected queries get up to `MAX_SLOT_RETRIES = 3` retries with verifier feedback before skip-and-tighten kicks in. The previous regex+stopword "topic guard" in `text_utils.py` has been retired.

**Document store** is SQLite-first. Databases live in `~/.local/share/document-store/{name}.db` (override with `DOCUMENT_STORE_DIR`; legacy `ANDAMENTUM_DATABASES_DIR` is also honoured). Ingestion is two-phase: document registered immediately (FTS5-searchable), chunks + embeddings written in a background pass that `repair()` can resume after a crash.

**Deferred ingestion** (capture now, enrich later) lets the expensive work be queued and drained on a schedule. `ingest(..., process="defer")` registers + FTS-indexes only — no LLM call — and marks the document `pending_enrich`; `ingest_source(database, path_or_url)` queues a source as `pending_source` for later conversion. Note the asymmetry (measured, `H-a5`): only `ingest` gives immediate keyword-searchability — an `ingest_source` row holds `markdown_content=''`, so it returns zero FTS hits until the drain converts it. **Queued documents are kept out of the RRF fusion and appended below it instead.** A document with no chunks can only ever match one of the four signals, so summing reciprocal ranks across all four reads its missing index as three rejections and buries it; the fusion is therefore restricted to `ingest_status='complete'`, and `search_pending_keyword` retrieves the rest into a labelled tail that occupies at most `limit // 5` slots (`search.py`). Tail results carry the ingestion status as their `match_type` and a `warning` naming the remedy — no new field, and no second vocabulary for a state the queue already names. `pending_source` rows are excluded outright by a `markdown_content != ''` predicate: their only indexed text is a filename-derived title, which BM25's length normalisation ranks top on a title-shaped query while there is nothing behind it. A database with an empty queue ranks exactly as it did before the tail existed. `process_pending(database, ...)` drains the queue (`pending_source` →convert→ `pending_enrich` →enrich→ `complete`), one document at a time, committing each transition as it completes — so a run is **resumable** (call it again), **pausable** (`should_continue` / `max_docs` / `max_seconds`), and loses at most one document's compute on a hard kill. `pending_status()` reports queue depth without touching a model; `retry_failed()` requeues failures (which are recorded on the row in `ingest_status`/`ingest_error`, never silently retried). Conversion is **injected** via `convert_fn`, so the store core never imports `harvest`; `document_store/pipeline.py` is the ONLY place `harvest` is imported and simply pre-fills that parameter — an app may call the core directly with its own converter. Converting *outside* the drain (calling harvest yourself, then `ingest()`) is not checkpointed and re-parses in-flight documents after an interruption. The `repair()` crash-sweep deliberately skips `pending_*` documents so an interactive `search()` never turns into a synchronous drain of the backlog. CLI: `andamentum-docstore ingest --defer | ingest-source | status | process-pending | retry-failed` (SIGINT/SIGTERM pause cleanly). The store owns a drainable queue, not a scheduler — cron/launchd supplies the clock. **Ingest never calls an LLM.** The store persists, chunks and embeds text; it does not author metadata. Per-chunk LLM tagging (`topics`/`people`/`has_decision`/`has_action_item`) was removed — nothing read those fields, and they cost ~93% of ingest wall-time (measured 283s -> 3.5s on the same arXiv paper, an 81x speedup, retrieval unchanged). The metadata vocabulary belongs to consumers, who write it via `ingest(metadata=...)`/`update_metadata()` and query it with `find_by_metadata` (deterministic, no LLM). `extract_document_metadata` remains an opt-in utility if you want a generated title. Consequently `ingest`, `process_pending`, `repair` and `reembed_document` take **no `model` argument** — only `embedding_model`; `search` still takes `model` for query planning. Chunking goes through `andamentum.chunker.extract_units` with `target_max_chars=4000`; the `Unit → Chunk` adapter (`chunker_adapter.py`) recovers full heading-breadcrumb `section_path` values via the chunker's structural API. Search fuses four signals via RRF: FTS5 keyword, chunk embeddings, doc embeddings, and DHP (temporal clustering, see `dhp.py`). Requires Ollama running locally with `embeddinggemma:latest` for embeddings.

**Retrieval is two-stage, and the second stage is never automatic.** `search` ranks documents by an RRF sum, which is built from ranks: it orders one query's results and nothing more. It has no absolute meaning, two queries' scores are not comparable, and it cannot answer "is result 7 relevant or merely seventh" — so every caller has to guess a `limit`. The second stage answers that question. `get_chunks(database, doc_id=...)` enumerates a document's passages in order and `get_chunk(database, chunk_id=...)` resolves one back later (`chunk_hits.py`); `rerank(query, texts, reranker_model=...)` scores them with a cross-encoder and `select_relevant(scored, min_relevance=..., buffer=...)` decides how many to keep (`reranking.py`). Chunk hits also ride out of `search` on `SearchResult.chunks` for documents the chunk signal matched — accumulated per document rather than collapsed with it, since the chunk signal emits one result per *chunk* and fusion is per *document*; the same document arriving three times would otherwise lose two real passages invisibly.

Four decisions in that design are load-bearing. **The chunk id is `"{doc_id}:{chunk_index}"` — a coordinate, not a content hash.** It survives re-embedding (which rewrites every AUTOINCREMENT row id and leaves positions alone), and it does not survive re-chunking; a caller who must detect that compares `ChunkHit.content`. The row id is deliberately not the public id because it is stable across strictly less. **`search` must never call `rerank`.** A cross-encoder is a 0.6B model resident in this process for its lifetime, on a memory budget nothing in `ollama ps` accounts for; a default rerank would charge every CLI and every pipeline that calls search repeatedly, and would make results depend on which extras happen to be installed. `tests/test_search_chunk_hits.py` fails if anyone wires it in. **`min_relevance` and `reranker_model` have no defaults.** A score's scale belongs to one specific model, so a floor calibrated elsewhere is a domain assumption wearing the clothes of a constant — `SUGGESTED_RERANKER_MODEL` is a suggestion no function reads. **The elbow cut and the absolute floor are both required and neither is redundant.** Normalising near-identical noise to [0, 1] manufactures visible structure: measured, 50 near-zero scores produce a confident-looking elbow that keeps a quarter of them, and only the floor excludes that. The elbow also errs generous by up to one item structurally — it finds the *corner*, and an index cannot say whether the corner is the last good item or the first bad one — so a clean five-good-then-thirty-bad curve keeps six. Do not tune that away; the floor removes the extra on evidence.

**Typeset module** (`andamentum.typeset`) — a standalone typesetting system with 7 visual atoms (`heading`, `prose`, `callout`, `items`, `aside`, `card`, `reference`), 3 named styles (`article`, `cv`, `report`), and HTML + PDF output. Used by the epistemic audit report (`epistemic/audit_report.py`, the only HTML renderer in the epistemic pipeline — the prose-led `typeset_report.py` was retired when the audit layout reached production), by `whetstone` for its HTML review output, and by `scribe` for its HTML/PDF render path. The epistemic data schema (the dataclasses consumed by the renderer) lives in `epistemic/report_data.py`. See `src/andamentum/typeset/USAGE.md` for the full API reference.

**Whetstone module** (`andamentum.whetstone`) — structured criterion-cascade review over drafts the user wrote themselves. Public entry: `await review_document(source, *, model)`. Implementation is a pydantic-graph DAG inside `whetstone/v3/` — sectionize → extract claims → build document model → run-criteria cascade → verify findings → gap-loop re-grounding → consolidate → 3-node optional novelty check → gate → synthesise → critique-and-revise → optional editor → finalize. Renderers (`render_markdown`, `render_html`, `render_docx`) consume the resulting `ReviewResult` unchanged. **The reviewer reads the text of the document being annotated** (`whetstone/reviewed_document.py`): a `.docx` input is reviewed as the atom projection of its own paragraphs and sectionised by its Word heading styles; any other input is harvested to markdown, written out as a baseline `.docx` FIRST, and then reviewed as *that* file's projection. Either way `Quote.char_start` / `Edit.char_start` are offsets in the whole reviewed document and therefore atom indices in the file being written, so `render_docx` converts them to spans and `whetstone.docx.annotate.apply_annotations` places them with no search, no normalisation and no threshold — a document that does not project to exactly the reviewed text raises `CoordinateError` rather than falling back. (The predecessor searched a converted rendering for the quote text and lost 15 of 43 rewrites on one real manuscript, every miss reporting a nearest match ≥0.97.) The `DocumentPatch` / `text_pattern` path survives ONLY for `andamentum-whetstone apply-patches`, whose input has no coordinates. **Sequential rounds fall out of that same rule and need one parameter, `author`** (`render_docx(..., author=...)`, `--patch-author NAME --allow-author-override` on the CLI, accepted on the review path as well as `apply-patches`): reviewer B's input is A's output, the projection excludes `<w:del>` and includes `<w:ins>`, so B reads the text as Word shows it with A's changes accepted and B editing text A inserted nests as `<w:ins A><w:del B>` — Word's own markup — without a line of round-2 code. There is deliberately no `--round`, no `sequential` mode and no `author=` on the review entry points. Three things make it hold: a prepended review report is bracketed by an `andamentum_review_report_N` bookmark and skipped by `reading.body_paragraphs`, so it is in the file but not in the next round's reading (reports STACK — an earlier report is the earlier reviewer's record; a damaged bookmark fails OPEN); `surgery.next_change_id` and `DocxEditor._next_comment_id` allocate above whatever ids the file already holds, because Word groups a revision by `w:id` and a restart at a fixed base made accepting A's insertion accept B's deletion of it. The same name twice is valid and produces unique ids, but Word groups changes only by author, so the two rounds are indistinguishable in the reviewing pane — pass a different name. Document type routes to one of six pluggable criterion sets via the classifier in `whetstone/_document_type.py`; an unknown type falls back to `GENERAL`. Caller can override the active criterion set with `criteria=[Criterion(...)]` or pass free-text reviewer guidelines via `guidelines_text="..."` (one LLM call decomposes them into a criterion list). Confidentiality-marker tripwire (`whetstone/_confidentiality.py`) refuses to run on peer-review material; `--confirm-own-draft` bypasses. Panel mode (multi-expert simulated peer review) is its own graph in `whetstone/v3/panel/` — different shape (N expert biosketches × N independent reviews + 1 synthesis) — invoked via `run_panel` / the `andamentum-whetstone panel` subcommand. Checklist mode is a third graph in `whetstone/v3/checklist/` — sectionize → extract claims → build document model → run probes → verify → corroborate → build result, linear, no loops — invoked via `run_checklist` / `checklist_document` / the `andamentum-whetstone checklist` subcommand. Each `Probe` (`checklist/probes.py`) names one defect class and carries a `quota` (`3` = "find the 3 most serious"; `None` = "report every instance, empty list if none"), and one of two shapes: `presence` findings ship a verbatim quote and are anchored by `locate`, `absence` findings ship the missing item plus 2–4 search terms and are DROPPED when any term turns up in the source (conservative by construction — a false "you never state your sample size" is the worst thing this mode can emit). `checklist/bank.py` holds fourteen distinct default probes — a nine-id core, re-skinned academic vs general, plus five per-type additions — routed by the same six document types (`probe_bank_for`, unknown type → `GENERAL_PROBES` with a warning), so a bank is nine to eleven probes; a caller with a house checklist passes `probes=[Probe(...)]` instead. Co-detections are cross-linked (`corroborated_by`) and never merged, the summary is a computed coverage table in bank order where a crashed probe reads `not run` and never `0`, and the confidentiality tripwire runs before any LLM call exactly as in review mode. `document_type` defaults to `"general"` in the library (no classifier call unless you pass `"auto"`) and to `"auto"` on the CLI. Style / readability checks (SMOG, weasel words, passive voice, etc.) are NOT bundled into the review pipeline — use the separate `andamentum.proofread` module or the `andamentum-whetstone proofread <source>` convenience subcommand. The legacy v1 + v2 surfaces (lens-based section-by-section pipeline, `--mode guidelines/custom/panel` flags, `--perspectives`, `--no-challenge`, `--embedding-model`, `--no-proofread`, `--persist-novelty-cache`) were removed during the v3 consolidation; the active code lives under `whetstone/v3/`.

**The goal loop** (`whetstone/goal/`, `await run_goal_loop(document, GoalSpec(...), *, model=...)`, `andamentum-whetstone review --goal "..." --goal-check KIND --max-rounds N`) sets a win condition and runs review → edit → re-review until it holds, rather than the fixed single pass every other mode makes. It is a plain bounded loop over functions the review path already has — `review_document_v3`, the same round trip sequential reviewers use (`reviewed_document.carry_forward_edits`, the `_carry_forward` this lifts out of the CLI) — not a second pydantic-graph graph, because a bounded generate-check-retry loop is ordinary control flow under `agentic_dialect` law 5/9, and the one genuinely stateful step is `review_document_v3` itself, called once per round. Four check kinds, chosen by `--goal-check`: `judged` (default) sends `--goal`'s text to `llm_judge.judge_score` as one criterion, in a separate call every round — never the pass that wrote the edit; `structure` reads the round's own `ReviewResult.findings` and is satisfied when the *active* review criteria (whatever `--reviewer`/`--criteria` already selected) raise nothing major or moderate — pair it with `--reviewer reader` for "the flow is correct"; `citations` (`goal/citations.py`) is a new deterministic text scan cross-checking in-text numeric-bracket or Pandoc `[@key]` markers against a reference-list section found by heading title — structural only, never whether a citation says what the sentence claims, and author-year markers are out of scope for the same reason; `figures` (`goal/figures.py`) is the one genuinely new, narrowly-scoped piece — the caller names each figure explicitly (`--goal-figure "Figure 1=fig1.png"`, `--goal-figure-model`), a regex locates its caption and the sentences that mention it (`locate_figure_mentions`), and `vision_critique.critique_figure`'s existing `extra_context`/`schema` parameters carry that text alongside the image; nothing inside `vision_critique` changes, and whetstone does not discover embedded images or associate a caption on its own. A goal counts as met only once its check passes twice in a row, confirming the next round's ordinary edits (which may touch criteria unrelated to the goal) did not undo it — the satisfying round's own edits are then discarded, and when the goal already holds with nothing left to edit, the same text is reviewed again for that second confirmation rather than reading "nothing to change" as stalling. The loop never raises on non-convergence: it always returns a typed `GoalRunResult` (`goal_met`, `stopped_reason` ∈ `{goal_met, no_progress, cap_reached, unresolvable}`, every round's full `ReviewResult`), and a non-`goal_met` stop appends one `AuthorQuestion` naming what it could not settle — the first real producer of a schema field that has existed since Phase 1 but that nothing in v3 populated. `no_progress` covers a round with no edits (only when the goal is not yet met — see above), edits with no net effect on the text, or the draft alternating between two prior states (checked against the last two rounds, not only the immediately preceding one); `unresolvable` is checked once, before spending any round, for a check that cannot be evaluated at all (no reference section for `citations`, a named figure never mentioned for `figures`) — zero rounds run, zero calls made. The CLI maps a non-`goal_met` stop to exit code 4, distinct from exit 3 (the pipeline itself crashed): the output is still written and still real, the code only says the loop did not reach what was asked. `--goal` takes exactly one reviewer (no reconciling several reviewers' findings every round) and forces the editor on every round regardless of `--editor`.

**Figures module** (`andamentum.figures`) — publication-quality scientific figure generation. High-level entry point: `figure(data, *, kind="auto", style="npg", journal="default", horizontal=None, output="figure.pdf")`. Lower-level building blocks: `setup_style`, `get_palette`, `savefig`, `panel_label`, `shared_legend`, `despine` (in `style.py`); plot primitives in `plots.py`; auto-detection (chart kind, log scale, column roles, bar orientation, x-tick rotation) in `auto.py` and `advisor.py`; bootstrap stats in `stats.py`. Bar charts with many or long categorical labels auto-flip to horizontal (`recommend_horizontal_bars` in `advisor.py`); vertical bars auto-rotate x-tick labels when crowded (`recommend_label_rotation`). Both behaviours emit `advisor_notes` so the caller knows what was changed. The package was absorbed from `mosaic-figures` (uninstall the standalone tool with `uv tool uninstall mosaic-figures` once this branch lands). Scribe integration lives in `figures/scribe_glue.py`: `insert_figure(doc, section, *, output_dir, caption, label, **chart_kwargs)` renders a PNG and inserts a `Figure` block via `Document.insert_into_section`.

**Chunker module** (`andamentum.chunker`) — structural-first semantic chunker. Single entry point: `extract_units(source, *, target_min_chars=2000, target_max_chars=10000, embedding_fn=None, judge_executor=None, domain="general") -> ChunkingResult`. Pipeline (literature consensus, 2026): **Stage 1** — split at markdown headings (`structural.py`); **Stage 2** — for sections >`target_max_chars`, semantic-split at paragraph boundaries chosen by largest cosine drops between adjacent paragraph embeddings (`semantic_split.py`, defaults to local Ollama `embeddinggemma:latest` via `embeddings.py`); **Stage 3** (optional) — small LLM judge (`judge.py`) for cuts whose drop-percentile is in the grey zone (60–90th by default), answers `keep | merge`. The LLM is never the primary segmenter. Each unit's `text` is byte-identical to a source span. The legacy agentic `windowing.py`/`refinement.py`/`NextUnitResult` machinery has been removed; legacy kwargs (`primary_executor`, `window_size`, `lookahead`, `extension_chars`, `max_iterations`) are accepted on `extract_units` for backward compat but ignored.

**Harvest module** (`andamentum.harvest`) — universal source → markdown extraction. Single entry point: `await extract(source: str | Path, *, mode="fast") -> str`. Resolves URLs (httpx fetch with SSRF protection) and file paths to bytes + format (PDF / HTML / DOCX / PPTX / Markdown / plain via three-tiered detection: extension → MIME → magic-byte sniff). For PDF / DOCX / PPTX uses Docling.

**Two extraction modes, one `Literal` parameter** (`mode="fast" | "accurate"`, also on `extract_from_bytes` and as `--mode` on the CLI). `"fast"` is the default and runs docling's standard pipeline on **its own stock settings** — `do_ocr=True`, `TableFormerMode.ACCURATE` — so an unchanged call behaves exactly as calling docling with no options did. The only deviation is stage batch size (4 -> 8), which affects throughput and never output. That pipeline is already multi-threaded in docling 2.121.0 (`StandardPdfPipeline` is documented as "High-performance PDF pipeline with multi-threaded stages" and takes `ThreadedPdfPipelineOptions`); harvest did not add that.

**This is deliberate and load-bearing.** An earlier revision of this work set `do_ocr=False` and `TableFormerMode.FAST` in fast mode. Because every existing caller — `document_store` ingestion, `deep_research` PDF fetches, `whetstone` source reading, `andamentum-proofread` — reaches this path with no `mode` argument, that silently broke every scanned PDF and downgraded every table in the repo. `tests/test_vlm_live.py:test_fast_mode_keeps_doclings_own_defaults` is the regression guard; do not "optimise" those two settings back.

**`ocr=False`** (CLI `--no-ocr`) is the opt-in born-digital speed path: a PDF that already has a text layer gains nothing from OCR, and OCR is the expensive stage. A scan read with `ocr=False` produces no text, and the backend raises `ExtractionError` naming the flag first and `mode="accurate"` second (`_has_text` strips `<!-- image -->` placeholders before the empty check, because placeholder-only output is non-empty as a string and empty as a document). `ocr` has no effect in accurate mode — the VLM pipeline has no OCR stage. `"accurate"` runs docling's **VLM pipeline**: `VlmConvertOptions.from_preset("granite_docling")` replaces the whole layout + OCR + TableFormer stack with one 258M model emitting DocTags, which round-trips into a `DoclingDocument` rather than being reconstructed from markdown, and `do_picture_description` adds a written description of every figure from SmolVLM-256M. Engine selection is `AutoInlineVlmEngineOptions` — one code path that resolves to MLX on Apple silicon and Transformers elsewhere; the resolved engine is logged because the gap is not marginal (docling's own benchmark: 6.2 s/page under MLX against 102 s/page under Transformers on an M3 Max). **Two docling defects had to be worked around to make figure descriptions happen, and both were found by the live test, not by reading the API.** First, `VlmPipeline.__init__` calls `super().__init__()` — which builds `enrichment_pipe` from `do_picture_description` — and then overwrites the whole list with `[]` (`docling/pipeline/vlm_pipeline.py:95`). The description model is therefore constructed, loaded and discarded, and the options are accepted and inert with no warning; `StandardPdfPipeline` keeps the list (`*self.enrichment_pipe`), which is why descriptions work there. `_describing_vlm_pipeline()` subclasses `VlmPipeline` and puts the stage back. Second, the crops that model reads only exist when `generate_picture_images=True` (`vlm_pipeline.py:325`). **Do not set `images_scale`** — a value of 2.0 gave a correct figure description but collapsed the body text to axis tick labels and an empty heading, because the page-image scale changes the coordinate frame the VLM emits boxes in and `force_backend_text` reads the text layer back through those boxes.

Figure descriptions reach the markdown because `export_to_markdown`'s `include_annotations` defaults to True. Marking them is done by `_mark_figure_descriptions`, which wraps `item.meta.description.text` in `<!--<annotation kind="description">-->…<!--<annotation/>-->` before export, so **a model-written description can never be mistaken for the author's own prose** downstream — a reviewer, a claim extractor or a search index would otherwise read a 256M model's guess about a chart as the author's own statement. The wrapper is docling-core's own marker format, reused verbatim so consumers need one vocabulary. The export flag `mark_annotations=True` is passed as well but only covers docling's deprecated `item.annotations` path: the live path writes to `item.meta`, and `docling_core/transforms/serializer/common.py:733` returns False — skipping the branch that honours the flag — as soon as `item.meta` is set. The two paths are mutually exclusive, so nothing is marked twice.

**Which model writes the descriptions is the `figure_model` parameter** (`extract`, `extract_from_bytes`, `--figure-model`), and it takes one of two shapes. A docling preset id (`smolvlm` / `granite_vision` / `qwen` / `pixtral`) downloads weights and runs them in-process. **`ollama:<model>`** instead reaches a vision model an existing local Ollama already serves — nothing downloaded, nothing loaded into this process, `concurrency` pinned to 1 (Ollama serialises same-model calls anyway), and `enable_remote_services=True` set for that path ONLY, since turning it on unconditionally would quietly widen what the whole pipeline may do. One prompt (`_FIGURE_PROMPT`) is used for every model — the preset's own wording is overwritten on `model_spec.prompt` — so swapping models compares models rather than prompts.

**Measured, not assumed.** Same figure (a bar chart with known values 4/9/17/28), same prompt, scoring eight facts a correct description must recover:

| `figure_model` | Score | Wall time | Peak RSS (this process) |
|---|---|---|---|
| `ollama:qwen3.8:27b-mlx` (**default**) | **8/8** | 27.3 s | 1.8 GB |
| `ollama:minicpm-v4.6:1b` | 6/8 | 27.7 s | 1.8 GB |
| `smolvlm` (256M, bundled) | 4/8 | 12.0 s | 2.7 GB |

Two counterintuitive results drive the default. A 27B model is **no slower** than a 1B one here — the description is a small fraction of wall time, most of which is docling converting the page — and an Ollama-served model costs this process **less** memory than the bundled 256M preset, because the weights live in Ollama. SmolVLM is not merely vaguer: on the fixture it reported "three different weeks" for a four-bar chart and invented bar values, which is worse than no description on a scientific figure.

**The default is deliberately not self-contained**, and that is a real cost accepted knowingly: `ollama:qwen3.8:27b-mlx` must already be pulled into a running local Ollama, so a fresh machine or a CI box cannot run accurate mode without passing `figure_model`. `_check_ollama_model` runs a preflight against `/api/tags` before any conversion starts and raises `OllamaUnavailableError` (a subclass of `ExtractionError`, so existing handlers keep working) naming the exact remedy — `ollama serve`, `ollama pull <model>`, or `figure_model='smolvlm'`. A reachable Ollama that lacks the model is a **hard error, never a silent substitution**: swapping in another model would change what every figure description says without the caller knowing. `ollama show <model>` must report the `vision` capability; the gemma4 family does not have it. Accurate is PDF-only — docling's DOCX / PPTX / HTML backends are not paginated, so the VLM has no page images to read and those formats run the standard pipeline in either mode (logged at INFO, not an error). It is roughly an order of magnitude slower per page: not the thing to point at a directory of 500 PDFs.

`force_backend_text` is **decided per document, not configured**. `harvest/pdf_probe.py:has_text_layer` samples the leading 5 pages with `pypdfium2` (docling's own PDF backend, so no docling/torch import for the probe) and requires a mean of 100 extractable characters per page — a typeset paper runs 2000–4000, a scan runs 0, so the threshold has a wide margin. A text layer present → `force_backend_text=True`: deterministic extraction for normal text, and only figures and tables go through the model, which is what keeps a 258M model from inventing a word in body text where nobody would notice. Absent → `False`, and the model reads the page end to end. A probe that raises answers `False` (the branch that still produces output) and logs a warning with a traceback — it picks between two working configurations and must never be the thing that fails a run.

The optional dependencies live in the **`vlm` extra** (`uv sync --extra vlm`): `docling[vlm]`, `transformers`, and `mlx-vlm` on Apple silicon only. **The `docling>=2.121.0` floor in the core dependencies is load-bearing and must not be lowered.** mlx-vlm 0.6.16+ requires `transformers>=5.14` while docling 2.97+ requires `transformers<5.9`; with a lower docling floor the resolver settles that clash by silently downgrading docling to 2.96.1 the moment anyone syncs the `vlm` extra. The floor makes the incompatible mlx-vlm versions unsatisfiable instead, so the resolver picks mlx-vlm 0.6.4 and docling stays current. Verified working pairing: docling 2.121.0 + mlx-vlm 0.6.4 + transformers 5.8.1. `_require_vlm_extra` checks for them *before* docling starts loading weights and raises an `ImportError` naming the extra — without it a missing `mlx_vlm` on macOS silently drops to a Transformers engine an order of magnitude slower. The CLI maps that to its own exit code **4**, distinct from an extraction failure. Live model tests are marked `vlm` and deselected by default; every other harvest test stubs the backend and imports neither docling nor torch. For HTML, sniffs `og:type` / JSON-LD `@type` / `<article>` tag (`metadata.py`) and routes article-tagged pages to trafilatura, listing/index pages (`@type=WebPage|CollectionPage|ItemList|...`) to Docling. When metadata is ambiguous, races both extractors concurrently and picks the higher-scoring output (`scoring.py` weights heading count × 10 + paragraph breaks × 1 + char count × 0.001, penalises >5% link density, disqualifies output with zero headings AND zero `\n\n`). Loud failure model — `HarvestError` / `FetchError` / `UnsupportedFormatError` / `ExtractionError` are typed; the function never silently returns empty. Extraction backends in `backends/` are thin async adapters with the same `extract(data, source_url) -> str` shape so the orchestrator can race them generically.

**Scribe module** (`andamentum.scribe`) — block-based document authoring. Documents live in SQLite at `~/.local/share/scribe/<name>.db` (override with `SCRIBE_DIR`). Public entry point: `Document.create(title=..., database=..., scaffold="article" | None)`; mutate with `append`/`replace`/`replace_section`; render with `render(path, format="docx")`. Section operations (`list_sections`, `section`, `replace_section`) are derived from heading blocks — there is no separate sections table. Each block has an integer revision counter; `replace()` enforces optimistic locking via `BEGIN IMMEDIATE` and writes an audit row to `scribe_revisions`. Citations are Pandoc-flavoured `[@key]` spans extracted by regex; references live in their own table; `[verify]` and `[citation needed]` markers are recognised and reported by `validate()`. Inline markdown (bold/italic/code) renders as styled runs in `.docx`. `.docx` is the only format wired into `render()`; an internal block→atom mapping toward typeset HTML/PDF lives in `render_typeset.py` but is not yet exposed through the public API. Scribe replaces the standalone `document-tools:doc-draft` plugin for Word file authoring; `.pptx` stays out of scope.

## Design language (andamentum visual system)

The repo's visual design system lives in `docs/design/`. It covers both document rendering (the `.typeset-*` family used by `andamentum.typeset`) and broader app/UI surfaces (the `.am-*` family for chrome — buttons, sidebars, chat, tool logs, settings, modals).

| File | What it is |
|---|---|
| `docs/design/components.css` | The complete stylesheet — all tokens + all components, light + dark via `data-theme`. Heavily section-commented. |
| `docs/design/DESIGN.md` | The *why*: vibe, palette logic, density rules, tone of voice, do's and don'ts. |
| `docs/design/CLAUDE.md` | Operating instructions for agents — surface→class cheat sheet, rules for new components, explicit list of things to refuse (gradients, drop shadows on cards, emoji icons, saturated semantic colours, pill buttons, etc.). |
| `docs/design/showcase.html` | Live visual reference for every component. |
| `docs/design/snippets/` | One copy-paste HTML file per component. |

When working on HTML output, CSS, or any new visual surface, **read `docs/design/CLAUDE.md` and `docs/design/DESIGN.md` first.** Match the system rather than inventing new selectors, colours, or spacing. The system uses CSS custom properties (`--am-*`) for every colour, size, and gap — never write raw hex codes or pixel values when a token exists.

**Spec vs. live implementation.** `docs/design/components.css` is the canonical specification of the visual system. `src/andamentum/typeset/styles.py` is the live CSS that the renderer compiles into output today. They are not yet in sync — the design directory is the source of truth that `styles.py` should converge toward. When making visual changes, edit the spec first; the migration from `styles.py` to `components.css` is a separate, larger piece of work.

## Working in git worktrees

When you need a worktree (e.g. for executing a multi-step plan in isolation), create it **inside this repo at `.worktrees/<feature-name>/`** — never as a sibling directory like `../andamentum-<feature>/`. Sibling worktrees fall outside Claude Code's permission scope and force the user to manually approve every single tool call.

`.worktrees/` is gitignored, so the nested worktrees don't pollute git status. Standard commands:

```bash
git worktree add .worktrees/<feature-name> -b <branch-name>
# ... do the work ...
git worktree remove .worktrees/<feature-name>
git branch -d <branch-name>  # after merging back
```

## Known quirks

- `pytest.ini_options.testpaths = ["src/andamentum"]` — tests live next to the code they test, not in a top-level `tests/` directory.
- `asyncio_mode = "auto"` — async tests don't need `@pytest.mark.asyncio`.
- Tests marked `@pytest.mark.ollama` or `@pytest.mark.benchmark` are deselected by default (`addopts = "-m 'not ollama and not benchmark'"`). Run explicitly with `uv run pytest -m benchmark`.
- `@pytest.mark.rerank` is deselected for the same reason as `vlm`: those tests download a real cross-encoder (~2 GB) and need the `rerank` extra. Run them with `uv run pytest -m rerank`. Every other reranking test stubs the model, and `select_relevant` is tested with no model at all — it must keep working on an install without the extra.
- `@pytest.mark.vlm` is deselected too: those tests run a local vision-language model for `harvest` accurate mode, downloading weights and holding over a GB. Run them explicitly with `uv run pytest -m vlm`. Keep new harvest tests out of that marker by stubbing the backend — the default suite has to stay cheap enough to run while other models are loaded on the same machine.
- WeasyPrint's flex layout breaks when `<p>` tags are inside flex children. The typeset renderer strips `<p>` wrapping from item and reference bodies as a workaround.
